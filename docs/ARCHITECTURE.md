# Архитектура ZzzEngine & WPF Editor

Единый источник правды по архитектуре, подсистемам, стандартам интерфейса и техническому долгу проекта.

---

## 1. Система Скриптинга и .meta/GUID Ассетов

### 1.1. Архитектура системы скриптов

#### 1.1.1. Четыре вида скриптов
Движок поддерживает 4 типа скриптов для реализации игровой логики:
1. **`zzz::script::GameScript` (Глобальный скрипт):** Не привязан к сцене или объектам. Существует на протяжении всей работы приложения. Идеально подходит для написания менеджеров (аудио, сохранения, глобальный стейт).
2. **`zzz::script::SceneScript` (Скрипт сцены):** Привязан к конкретной сцене (карте). Живет, пока активна сцена. Подходит для логики уровня, спавнеров и квестов.
3. **`zzz::script::Script` (Компонентный скрипт / MonoBehaviour-like):** Привязывается к конкретному `GameObject` на сцене. Подходит для контроллеров игрока, поведения ИИ.
4. **Обычные C++ классы и структуры:** Обычные C++ классы, структуры данных или математические хелперы свободно используются внутри движковых скриптов как обычный C++ код.

#### 1.1.2. Создание скриптов
При создании через интерфейс редактора:
- Автоматически генерируются файлы `.hpp`, `.cpp`, `.meta` с уникальным GUID.
- Скрипт автоматически прописывается в реестре `RegisterAllScripts.cpp`.

#### 1.1.3. Модель исполнения: Компиляция vs Рантайм
- **Компиляция (Собираем всё):** В общую библиотеку (`scripts.dll`) **включаются все скрипты** проекта. При этом сама система сборки поддерживает инкрементальную компиляцию — пересобираются только измененные файлы.
- **Рантайм (Работает только нужное):** Отрабатывают только те скрипты, которые явно затребованы игрой: прописанные в глобальном `GameConfig`, прикрепленные к активной сцене или к существующим объектам.

### 1.2. Механизм Регистрации и Шаблоны

Скрипты регистрируются явно через автоматически генерируемый файл `.editor/RegisterAllScripts.cpp`.
Шаблонный метод `ScriptRegistry::Register<T>(name)` на основе базового класса `T` регистрирует скрипты в одну из трех категорий: `s_GameScriptFactories`, `s_SceneScriptFactories`, `s_ScriptFactories`.

Новые скрипты создаются из шаблонов в `src/editor_dll/templates/scripts/`:
- `{Type}.hpp.template` / `{Type}.cpp.template`

---

### 1.3. Система `.meta`-файлов и GUID Ассетов

Каждый ассет хранит стабильный GUID в соответствующем файле `.meta` (формат TOML):

```toml
guid = "b5f36e84-18c7-4fd9-b22e-a567df489bc3"
class_name = "Player"
namespace = "Gameplay"
```

- Paths (пути) могут меняться при перемещении или переименовании; GUID не меняется никогда.
- Все ссылки в конфигах (`game_config.toml`) и сценах должны строиться исключительно на основе GUID.
- Единая точка чтения/записи формата `.meta` — класс `AssetMetaFile` (`src/tools/editor/Services/Project/Infrastructure/AssetMetaFile.cs`).

---

### 1.4. Горячая перезагрузка (Hot-Reload)

В редакторе скрипты собираются в `scripts.dll` посредством вызова CMake в фоновом режиме:
1. `FileSystemWatcher` отслеживает изменения в `Assets/`.
2. После окончания ввода (через debounce 500мс) запускается фоновая компиляция `.editor/bin_build/scripts.dll`.
3. Редактор выгружает текущую библиотеку, обновляет бинарник и через `LoadLibraryA` инициализирует свежий `RegisterAllScripts()`.

## 2. Модель Ресурсов (Resource Model)

### 2.1. Границы ресурсов (Scope)
- Только файлы под директорией `Assets/` являются пользовательскими ресурсами.
- Конфигурации системы вне `Assets/` (например, `Configs/project_config.toml`, `Configs/game_config.toml`) являются инфраструктурой проекта.
- Папки **не являются ресурсами** (не имеют GUID, не имеют типа ассета).

### 2.2. Типы ресурсов (`AssetResourceType`)
Типы ресурсов описываются перечислением `AssetResourceType`:
- `Script`, `Scene`, `Texture`, `Material`, `Model`, `Audio`, `Shader`.

Фильтрация в дереве ассетов происходит по типам ресурсов, а не по названиям корневых папок.

## 3. Стандарты UI Редактора (UI Guidelines)

### 3.1. Текстовые поля и списки (`TextBox`, `ComboBox`)
- **Границы по умолчанию:** Прозрачные (`Transparent`) рамки во избежание визуального шума.
- **Фокус:** Синяя рамка (`Brush_Accent`) появляется только при фокусе (`IsKeyboardFocusWithin="True"`).
- **Валидация:** При ошибке используется `IndianRed`. При успехе рамка сбрасывается (`ClearValue`).

### 3.2. Диалоговые и Инструментальные Окна
- Все диалоги (`NewProjectDialog`, `NewScriptDialog` и др.) используют рамку в 1 пиксель цветом `Brush_Text_Primary` в стиле основного окна.

## 4. План Развития и Технический Долг (Roadmap / TODO)

### 4.1. Архитектурные задачи
1. **Переход на ECS вместо `shared_ptr<Script>` на `GameObject`:**
   Перевод компонентных скриптов на ECS (свой / EnTT / flecs) для обеспечения cache-friendly аллокаций.
2. **Сохранение состояния при Hot-Reload (State Restore):**
   Сериализация полей скриптов перед выгрузкой `scripts.dll` и их последующая десериализация.
3. **Единый стиль обработки ошибок:**
   Унификация использования `std::expected`, `throw` и `ensure`. Введение единого `Z_FATAL` или полный переход на `std::expected` с кодами ошибок `ErrorCode`.
4. **Покрытие тестами (`src/qa/`):**
   Написание тестов для `ScriptRegistry`, `.meta`/GUID синхронизации, логгера и команд Undo/Redo.
