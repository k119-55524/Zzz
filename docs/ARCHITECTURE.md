Единый источник правды по архитектуре, подсистемам, стандартам интерфейса и техническому долгу проекта.

## 1. Система Скриптинга и .meta/GUID Ассетов

### 1.1. Архитектура системы скриптов

#### 1.1.1. Четыре вида скриптов
Движок поддерживает 4 типа скриптов для реализации игровой логики:
1. **`zzz::script::GameScript` (Глобальный скрипт):** Не привязан к сцене или объектам. Существует на протяжении всей работы приложения. Идеально подходит для написания менеджеров (аудио, сохранения, глобальный стейт).
2. **`zzz::script::SceneScript` (Скрипт сцены):** Привязан к конкретной сцене (карте). Живет, пока активна сцена. Подходит для логики уровня, спавнеров и квестов.
3. **`zzz::script::Script` (Компонентный скрипт / MonoBehaviour-like):** Привязывается к конкретному `GameObject` на сцене. Подходит для контроллеров игрока, поведения ИИ.
4. **Обычные C++ классы и структуры:** Обычные C++ классы, структуры данных или математические хелперы свободно используются внутри движковых скриптов как обычный C++ код.

#### 1.1.2. Создание скриптов
При создании через интерфейс редактора:
- Автоматически генерируются файлы `.hpp`, `.cpp`, `.meta` с уникальным GUID.
- Скрипт автоматически прописывается в реестре `RegisterAllScripts.cpp`.

#### 1.1.3. Модель исполнения: Компиляция vs Рантайм
- **Компиляция (Собираем всё):** В общую библиотеку (`scripts.dll`) **включаются все скрипты** проекта. При этом сама система сборки поддерживает инкрементальную компиляцию — пересобираются только измененные файлы.
- **Рантайм (Работает только нужное):** Отрабатывают только те скрипты, которые явно затребованы игрой: прописанные в глобальном `GameConfig`, прикрепленные к активной сцене или к существующим объектам.

### 1.2. Механизм Регистрации и Шаблоны

Скрипты регистрируются явно через автоматически генерируемый файл `.editor/RegisterAllScripts.cpp`.
Шаблонный метод `ScriptRegistry::Register<T>(name)` на основе базового класса `T` регистрирует скрипты в одну из трех категорий: `s_GameScriptFactories`, `s_SceneScriptFactories`, `s_ScriptFactories`.

Новые скрипты создаются из шаблонов в `src/editor_dll/templates/scripts/`:
- `{Type}.hpp.template` / `{Type}.cpp.template`

---

### 1.3. Система `.meta`-файлов и GUID Ассетов

Каждый ассет хранит стабильный GUID в соответствующем файле `.meta` (формат TOML):

```toml
guid = "b5f36e84-18c7-4fd9-b22e-a567df489bc3"
class_name = "Player"
namespace = "Gameplay"
```

- Paths (пути) могут меняться при перемещении или переименовании; GUID не меняется никогда.
- Все ссылки в конфигах (`game_config.toml`) и сценах должны строиться исключительно на основе GUID.
- Единая точка чтения/записи формата `.meta` — класс `AssetMetaFile` (`src/tools/editor/Services/Project/Infrastructure/AssetMetaFile.cs`).
- В проекте действует **единое глобальное пространство GUID**: значение не может повторяться между сценами, представлениями, скриптами разных типов, ресурсами, слоями и объектами сцен. Это пространство идентичности не объединяет их runtime-хранилища и не отменяет проверку ожидаемого типа ссылки.
- GUID сцен, представлений, скриптов и файловых ресурсов хранится только в соответствующем `.meta`. GUID слоя и объекта является частью JSON сцены. Упаковщик не генерирует GUID и не меняет его при каждой сборке.
- До упаковки нативная часть Assets Builder собирает общий реестр `Guid -> владелец (тип, файл, JSON-путь)`. Пустой, некорректный или повторяющийся GUID останавливает сборку с указанием обоих владельцев конфликта. После построения реестра отдельным проходом проверяются существование и тип всех GUID-ссылок; C#-слой только запускает проверку и показывает её результат.

---

### 1.4. Горячая перезагрузка (Hot-Reload)

В редакторе скрипты собираются в `scripts.dll` посредством вызова CMake в фоновом режиме:
1. `FileSystemWatcher` отслеживает изменения в `Assets/`.
2. После окончания ввода (через debounce 500мс) запускается фоновая компиляция `.editor/bin_build/scripts.dll`.
3. Редактор выгружает текущую библиотеку, обновляет бинарник и через `LoadLibraryA` инициализирует свежий `RegisterAllScripts()`.

## 2. Модель Ресурсов (Resource Model)

### 2.1. Границы ресурсов (Scope)
- Только файлы под директорией `Assets/` являются пользовательскими ресурсами.
- Конфигурации системы вне `Assets/` (например, `Configs/project_config.toml`, `Configs/game_config.toml`) являются инфраструктурой проекта.
- Папки **не являются ресурсами** (не имеют GUID, не имеют типа ассета).

### 2.2. Типы ресурсов (`AssetResourceType`)
Типы ресурсов описываются перечислением `AssetResourceType`:
- `Script`, `Scene`, `Texture`, `Material`, `Model`, `Audio`, `Shader`.

Фильтрация в дереве ассетов происходит по типам ресурсов, а не по названиям корневых папок.

### 2.3. Потоковая синхронизация и гранулярность таблиц ресурсов (`ResourceTable<T>`)
- **Текущая архитектура (MVP / Этап 22):**
  - Каждый тип ресурса обслуживается отдельным экземпляром `ResourceTable<T>`, защищённым `std::shared_mutex m_Mutex`. Таблица хранит `std::shared_ptr<OneShotEvent<ResultType>>`.
  - **Строгое соблюдение Zero User Code Under Lock и ликвидация межменеджерного lock-order:** Замок таблицы $L1$ удерживается исключительно на время быстрого поиска/вставки `shared_ptr` в карту. Замок $L1$ **безусловно отпускается** ДО подписки (`Subscribe` идёт под локальным мьютексом события $L2$), ДО вызова инициирующей лямбды `onLoadRequest` и ДО `Resolve`.
  - За счёт этого вызов `CpuResourceManager::GetAsync` из лямбды `GpuResourceManager` происходит при полностью свободном замке GPU-таблицы: цепочка $L1(GPU) \to L1(CPU)$ отсутствует, взаимные блокировки невозможны.
  - Применён двухфазный **Read-First поиск**: чтение существующего `shared_ptr` выполняется под `std::shared_lock`, монопольный `std::unique_lock` берётся только при первом создании записи.
- **Известное ограничение масштабирования (Lock Contention):** Для текущих сцен (куб, базовые уровни) единый мьютекс корзины обеспечивает максимальную простоту и надёжность. Однако при высоконагруженном стриминге (тысячи ассетов открытого мира в секунду) единый замок на весь тип ресурса будет точкой конкуренции при массовых параллельных вставках новых GUID.
- **Целевая архитектура (Этап 58, TODO 27):** В рамках этапа 58 («Высоконагруженный стриминг ресурсов») запланирован переход на:
  - *Шардирование блокировок (Striped / Sharded Map):* разделение таблицы на $N$ независимых корзин (напр., 16/32) по хэшу `guid.Hash() % N` со своими мьютексами, полностью устраняющее соревнование за вставку разных ресурсов.

## 3. Стандарты UI Редактора (UI Guidelines)

### 3.1. Текстовые поля и списки (`TextBox`, `ComboBox`)
- **Границы по умолчанию:** Прозрачные (`Transparent`) рамки во избежание визуального шума.
- **Фокус:** Синяя рамка (`Brush_Accent`) появляется только при фокусе (`IsKeyboardFocusWithin="True"`).
- **Валидация:** При ошибке используется `IndianRed`. При успехе рамка сбрасывается (`ClearValue`).

### 3.2. Диалоговые и Инструментальные Окна
- Все диалоги (`NewProjectDialog`, `NewScriptDialog` и др.) используют рамку в 1 пиксель цветом `Brush_Text_Primary` в стиле основного окна.

### 4.1. Архитектурные задачи

1. **Исследование хранения компонентных скриптов (отложено).**
   ECS (свой / EnTT / flecs) не является принятым решением или обязательной заменой `shared_ptr<Script>`. Сначала рабочий жизненный цикл на существующих доменах (этап 23), затем измерения аллокаций, локальности и стоимости обхода. Менять модель только при подтверждённой необходимости; не блокировать куб и GUI.

2. **Сохранение состояния при Hot-Reload (этапы 41, 47).**
   Сериализация полей перед выгрузкой `scripts.dll` и восстановление после загрузки. Зависит от модели сериализуемых полей; безопасность удаления объектов и подписок до выгрузки DLL обязательна независимо от State Restore (п.12).

3. **Обработка ошибок: границы вместо новой глобальной системы.**
   Принято: ошибка обязательного меша, материала или текстуры пока приводит к `THROW_RUNTIME`, без запуска неполной сцены. Низкоуровневый I/O сохраняет существующие `expected`/коды ошибок; `ensure` служит внутренним контрактам, не проверке внешних файлов в Release. Ошибка worker-потока передаётся управляющему потоку; исключения не пересекают C/PInvoke. Учесть в этапах 16 и 19–20. Переход всей базы на `Z_FATAL` или `expected` не утверждён и не блокирует работу.

4. **Покрытие тестами (в составе каждого затронутого этапа).**
   Конкретные сценарии и объём определяются риском, а не требованием каждый раз запускать весь QA. До КП-1 (этап 25) проверить ресурсную цепочку, жизненный цикл скриптов, кадры, resize/minimize, смену сцены и закрытие окна при загрузке. Для этапов 17–18 отдельные unit-тесты пока не обязательны по решению пользователя: ядро ещё формируется; проверки и непроверенное фиксируются в плане этапа. Сборки выполняются по команде либо после крупных правок.

5. **`EventImpl`: разделить корректность и оптимизацию.**
   - Сохранение порядка вызовов при `BaseScript::SetActive(false/true)` проверить и определить в этапе 23: повторная подписка сейчас может менять порядок.
   - Производительность на больших наборах подписчиков исследовать отдельно по профилю. `memory_order_relaxed`, отказ от `weak_ptr::expired()`, paused-флаг, SoA и собственный delegate являются вариантами, не утверждённым набором правок.
   - Ослабление синхронизации или отказ от проверки lifetime требуют доказанного владения и безопасной отписки; микрооптимизация не заменяет этот контракт.

ArchiveWriter отвергает слишком длинные имена с логом и `false`, не пропуская исключение через PInvoke.

### 4.5. Жизненный цикл и открытые решения

20. **Обязательный жизненный цикл компонентных Script (этап 23, до куба).**
    `GameObject::~GameObject() = default`, полный путь вызовов OnStart/OnUpdate/OnDestroy ещё не доведён. Обеспечить однократные события, деактивацию/отписку и безопасное уничтожение при удалении объекта и выгрузке сцены. Отдельно обеспечить корректный обход при удалении/смене родителя из callback. Реализовать поверх существующих доменов; ECS из п.1 и шина на каждый объект не являются обязательными решениями.

20.1. **Хранение и поиск в ObjectDomain (этапы 18 и 23).**
    В соответствии с Правилом 8.2:
    - Схлопнуть владение объектами в единое хранилище `std::unordered_map<Guid, std::unique_ptr<GameObject>> m_Objects` вместо двух параллельных карт `m_AllocatedObjects` и `m_GuidToObject`;
    - Вторичный индекс поиска по имени `std::unordered_multimap<std::string, GameObject*> m_ObjectsByName` наполняется только при создании объекта;
    - Метод `SetName` ограничить контекстом редактора (Editor), исключив динамическую инвалидацию в рантайме;
    - Устранить пустой проход по всем `GameObject` в `ObjectDomain::Update()`, ограничив тики исключительно зарегистрированными активными подписчиками скриптов/систем.

20.2. **Оптимизация обхода dirty битовой маски в NodeStorage (этап 18).**
    - Исключить повторный пересчёт матриц: если грязный родитель уже обновляет своё поддерево, грязные потомки не запускают повторный обход того же диапазона;

25. **Архитектура IoScheduler, Backpressure и протокол остановки (этапы 22, 58).**
    - **Контекст и архитектурная модель:** Архитектура дискового ввода-вывода строится вокруг `IoScheduler`, который централизованно сериализует принятие решений, управляет приоритетными очередями и защищает память от переполнения (Backpressure). На этапе 22 по умолчанию используется политика одного блокирующего читателя (`SingleBlockingReaderPolicy`), исключающая seek-thrashing на HDD. Число физических I/O-запросов и степень параллелизма являются политикой бэкенда.
    - **Синхронизация очереди I/O и `m_IoCv`:** Очередь `DoubleBufferedVector` и условная переменная `m_IoCv` защищаются единым мьютексом `m_IoMutex` (producer вызывает `Push` под `m_IoMutex`, отпускает и делает `notify_one`; воркер засыпает на `m_IoCv.wait` с проверкой предиката строго под `m_IoMutex`), предотвращая потерю пробуждения (lost wakeup).
    - **Контроль памяти (Backpressure) и RAII-токены (`InFlightPermit`):**
      - Ограничение суммарного объёма сырых буферов в полёте (`m_MaxInFlightBytes`) и лимита запросов в полёте (`m_MaxInFlightRequests`). При превышении лимита (когда диск читает быстрее, чем воркеры парсят) `IoScheduler` приостанавливает чтение;
      - Для гарантированного возврата квоты памяти даже при исключениях используется RAII-объект `InFlightPermit`;
      - Пакетное ограничение (Batch Drain Limit) за одну итерацию;
      - Метрики для профилирования: глубина очереди (`queue depth`), байты в полёте (`bytes in flight`).
    - **Детерминированный порядок остановки подсистем (`Engine::Destroy`):**
      `Stop I/O` $\to$ `JoinAll()` воркеров $\to$ **`Очистка completion queues БЕЗ ИСПОЛНЕНИЯ`** $\to$ `WaitForGpu()` $\to$ `Clear tables` $\to$ уничтожение менеджеров. Вызов `WaitForGpu()` выполняется строго до очистки GPU-таблиц, чтобы GPU закончил обработку команд до разрушения буферов/дескрипторов. Исполнение колбэков после остановки воркеров строго запрещено, чтобы исключить постановку новых задач в остановленные пулы.
    - **Кадровое бюджетирование главного потока (Frame Budget):** В этапе 22 (загрузка стартовой сцены) очередь `CallbackQueue::ExecuteAll()` сбрасывает все накопленные колбэки за раз. При стриминге открытого мира (этапы 50/58) вводятся лимиты `ExecuteBudgeted(maxCount, maxDuration)`, чтобы сотни параллельных колбэков не вызывали просадки FPS (frame spikes).
    - **Оптимизации файлового доступа:**
      - Дескрипторы пакетов (`data.dat`, `package.dat`): поскольку `PackageManager` читается также из worker'ов загрузки сцен, постоянно открытые дескрипторы отложены до замеров производительности (этап 58) либо должны быть сделаны исключительной собственностью единственного `IoScheduler`; на этапе 22 доступ остаётся потокобезопасным без разделяемых потоками `ifstream`;
      - Пространственная группировка фоновых чтений по архиву и смещению;
      - Защита от голодания (`Anti-Starvation`) фоновой очереди при непрерывном потоке `High`;
      - **Эскалация приоритета (`Priority Promotion`):** если ресурс уже находится в состоянии `Pending` по низкоприоритетной заявке (`Background`), но затем запрашивается интерактивно (`High`), его заявка немедленно повышается до `High`, исключая зависание интерактивного запроса в медленной очереди.
    - **План развития:** В этапе 58 перевести бэкенд на нативные асинхронные интерфейсы ОС (Windows Overlapped I/O / IOCP, Linux/Android `io_uring`, DirectStorage для прямой загрузки в GPU) с сохранением контрактов `ResourceTable<T>` и `ResourceRef<T>`.

      1. В `OneShotEvent<T>` реализовать метод `HasActiveSubscribers()` (проверка живости контекстов подписчиков под мьютексом);
      2. В `IoReadRequest` добавить предикат отмены (`isAlive`), проверяемый перед чтением с диска (в `m_IoThread`), перед CPU-десериализацией (в воркере `TaskDispatcher`) и перед созданием GPU-буферов;
      3. При выгрузке сцены (`SceneManager::UnloadScene`) инвалидировать ассоциированные запросы за 0 мс, не выполняя паразитного чтения файлов и аллокаций VRAM.

27. **Таблицы ресурсов ResourceTable<T>: Zero User Code Under Lock, Read-First и развитие (этапы 22, 50, 58).**
    - **Контекст и синхронизация в этапе 22 (MVP):**
      1. **Zero User Code Under Lock:** $L1$-мьютекс `ResourceTable` захватывается исключительно на время поиска/вставки `std::shared_ptr<OneShotEvent>` в таблицу и **немедленно отпускается**. Ни `Subscribe` (вызывается под $L2$-мьютексом события), ни `onLoadRequest` (вызывается вне всех замков), ни `Resolve` не выполняются под замком таблицы.
      2. **Защита от «воскрешения» ресурсов (`Resolve` без `try_emplace`):** Записи в кэше неизменяемы до shutdown (`Clear()`). Метод `Resolve(guid, result)` выполняет `find` под `shared_lock`: если запись не найдена, результат отбрасывается. `Resolve` **категорически не создаёт** новую запись через `try_emplace`.
      3. **Единое хранение `DispatcherFunc` и контракт привязки потоков (Thread Affinity Contract):**
         - Диспетчер хранится как поле `ResourceTable<T>` и передаётся в `Subscribe` и `Resolve`.
         - В `CpuResourceManager` таблицы инициализируются диспетчером **пула воркеров (`TaskDispatcher`)**: колбэки подписчиков (включая `GpuResourceManager`) выполняются на фоновом воркере. Это гарантирует, что тяжёлая операция `GpuResourceBuilder::Build` исполняется **на пуле воркеров**, а не на главном потоке.
         - В `GpuResourceManager` таблицы инициализируются диспетчером **главного потока (`MainThreadQueue`)**: финальное уведомление подписчика сцены (`GameObject::OnMeshLoaded`) доставляется на главный поток без блокировки кадров.
      4. **Контракт гарантированного разрешения и перехват исключений (No-Hang Contract в состоянии Running):** Любой запрос ресурса, зарегистрированный в таблице как `Pending`, в состоянии `Running` обязан завершиться вызовом `Resolve` (успех или `std::unexpected`). Задачи в `IoScheduler` и воркерах `TaskDispatcher` оборачиваются в `try ... catch`, а результат `TaskDispatcher::Submit` проверяется для трансляции ошибок диска, десериализации, сбоев очередей и C++ исключений в `std::unexpected`, исключая «вечный лоадинг» и зависание барьеров инициализации (`AsyncInitTracker` / `CountdownTrigger`). При shutdown (`Engine::Destroy()`) незавершённые запросы отменяются без исполнения callbacks.
    - **План развития (этап 50 — Hot Reload и отмена):**
      - Внедрение монотонного счётчика `m_NextGeneration` и валидации поколений запросов для защиты от зомби-ресурсов при динамической перезагрузке;
      - Политика **Invalidate / Retry** с методом `Invalidate(guid)` / `Evict(guid)`, разрешающим старое событие отменой (`unexpected("Cancelled")`) вне замка таблицы;
      - Политика Permanent Failure vs Retry.
    - **План развития (этап 58 — Высоконагруженный стриминг):** Перевести `ResourceTable<T>` на шардированную структуру (Striped / Sharded Map с массивом из 16/32 мьютексов по `guid.Hash()`) для исключения lock contention при одновременном спавне сотен сущностей в открытом мире.

28. **Контракт потокобезопасности GPU-трансфера (GpuUploadScheduler), GpuResourceBuilder и разделение этапов 22 и 23.**
    - **Гарантии этапа 22 (Zero GAPI under workers, Stubs only):**
      1. На этапе 22 полностью исключены любые прямые вызовы графического API (`IGAPI`) из произвольных воркеров `TaskDispatcher`. Воркер пула создаёт исключительно платформенно-нейтральный C++ объект-заглушку `GpuMesh` (структура данных в оперативной памяти) и вызывает `Resolve()`;
      2. Событие `Ready` (`OneShotEvent` в `GpuResourceManager`) на этапе 22 означает **исключительно готовность объекта-заглушки**, а **не резидентность ресурса в видеопамяти (GPU residency)**;
      3. Объект `GpuMesh` удерживает `ResourceRef<CpuMesh> m_CpuMesh;` ([GpuMesh.h (line 25)](/C:/Workspaces/Zzz/src/engine/resources/gpu/GpuMesh.h:25)), инкрементируя внешний счётчик ссылок `m_ExternalRefCount` и защищая CPU-ресурс от преждевременной выгрузки до этапа 23;
      4. **Оркестрация vs Построение (`GpuResourceBuilder<T>`):** `GpuResourceManager` осуществляет общую оркестрацию асинхронных вызовов, а типоспецифичное создание GPU-объектов (меши, текстуры, шейдеры, материалы) инкапсулируется в трейты `GpuResourceBuilder<T>`.
    - **Архитектурный контракт этапа 23 (GpuUploadScheduler и GPU-синхронизация):**
      1. **Ограничения многопоточности современных GAPI:**
         - В **DirectX 12** разрешена параллельная запись в разные command lists, но `ID3D12CommandAllocator` и `ID3D12GraphicsCommandList` не являются свободно разделяемыми между произвольными потоками ([Microsoft D3D12](https://learn.microsoft.com/en-us/windows/win32/direct3d12/recording-command-lists-and-bundles));
         - В **Vulkan** очереди `VkQueue` и пулы команд `VkCommandPool` требуют строгой внешней синхронизации ([Vulkan Specification](https://registry.khronos.org/vulkan/specs/latest/html/vkspec.html)). Произвольный вызов GAPI из несинхронизированных воркеров `TaskDispatcher` приводит к race conditions и крашам;
         - Поэтому реальный GPU-трансфер (upload) на этапе 23 архитектурно реализуется через специализированный **`GpuUploadScheduler`** (координатор/выделенный конвейер upload с отдельной Copy Queue, copy command allocator/list и fence/timeline semaphore), а не через произвольные воркеры `TaskDispatcher` без дополнительного контракта.
      2. **Наступление истинного `GpuReady`:** Реальный статус `GpuReady` на этапе 23 наступает только после физического завершения выполнения copy-команд на GPU и подтверждения через fence / timeline semaphore;
      3. **Освобождение системной памяти (Drop CPU bulk data):** В этапе 22 `CpuMesh` остаётся в таблице `CpuResourceManager::ResourceTable<CpuMesh>` до shutdown (`Clear()`). Одиночного `m_CpuMesh.reset()` внутри `GpuMesh` недостаточно для освобождения системной памяти, поскольку ресурс удерживается в CPU-таблице. Полноценный механизм выгрузки / удаления записи из `CpuResourceManager` после успешного завершения upload проектируется и реализуется на этапе 23 вместе с конвейером видеопамяти.
          - Данные сохраняются только в исключительных случаях: при необходимости восстановления контекста при потере устройства (`Device Loss / Restore`) или в редакторе (Editor tools).

29. **Модель владения в ObjectDomain: `shared_ptr` vs Generational Handle (DOD-архитектура).**
    - В этапе 22 `ObjectDomain` переведён на `std::vector<std::shared_ptr<GameObject>>` исключительно ради безопасной подписки на асинхронные ресурсы через нативный `weak_from_this()`.
    - Для одиночных сцен и MVP это полностью безопасно и исключает use-after-free. Однако для масштабируемого Data-Oriented (DOD) движка хранение умных указателей создаёт оверхед контрольных блоков и нарушает локальность данных.
    - В долгосрочной дорожной карте оптимизации сцены зафиксирован переход на **Generational Handle (`index + generation`)**: подписка на ресурсы хранит handle сущности, а разрешение указателя на объект выполняется централизованно доменом сцены на главном потоке при получении колбэка.

30. **Безопасность файловых зон: Default Deny Allowlist и защита от Path Traversal.**
    - В `src/core/enums/eFileLocation.h` функция `IsLocationWritable` реализована по строгому принципу **Default Deny (явный allowlist)**: разрешены исключительно `User`, `Saves`, `Cache`, `Logs`. Зона `App`, а также любые неизвестные или добавленные в будущем значения перечисления безусловно считаются **Read-Only**.
    - В `FileSystemBase::WriteAllBytes` реализована защита от атак выхода за пределы каталога (Path Traversal): путь нормализуется, проверяется отсутствие выхода через последовательности `..`, и гарантируется, что канонический путь строго лежит внутри базового каталога разрешённой зоны. Попытки записи за пределы зоны блокируются с генерацией ошибки.

31. **Разделение ресурсных конвейеров: Графика (GpuResourceManager) vs Физика / Аудио / Скрипты (CpuResourceManager).**
    - **Изоляция визуальных и физических данных:**
      Графические ресурсы (`GpuMesh`, `GpuTexture2D`, `GpuMaterial`, `GpuShader`) оптимизированы для конвейера рендера (вершины с нормалями, тангентами, UV-координатами, LOD-ы, mip-уровни, дескрипторные таблицы). Физическим движкам (PhysX / Jolt) эти данные не нужны и вредны для кэша. Физика требует собственных структур: упрощённых выпуклых оболочек (Convex Hull), наборов примитивов (Box, Sphere, Capsule) либо легковесных треугольных сеток коллизий без текстурных атрибутов (`CollisionMesh`).
    - **Роли менеджеров:**
      1. **`GpuResourceManager`:** управляет исключительно графическими ресурсами, их дедупликацией по GUID в `ResourceTable<TGpu>` и жизненным циклом в видеопамяти (VRAM). `CpuMesh` в его конвейере — это промежуточный буфер десериализации в RAM (на этапе 22 удерживается в CPU-таблице до shutdown, механизм удаления записи из таблицы после upload проектируется на этапе 23).
      2. **`CpuResourceManager`:** управляет ресурсами, постоянно живущими в системной RAM для не-GPU подсистем (физические коллизии, аудиоданные, кривые анимаций, навигационные сетки). Запросы этих систем не смешиваются с графическим конвейером и загружаются через типизированный `CpuResourceManager::GetAsync<T>`.
    - **Инкапсуляция дискового бэкенда (Архитектурный контракт):**
      - Планировщик `IoScheduler` является приватным компонентом `CpuResourceManager` (`std::unique_ptr<IoScheduler> m_IoScheduler`). Вся работа с файлами, пакетами (`DataAssetsManager`, `PackageManager`) и управление потоком I/O сосредоточены на стороне CPU.
      - `GpuResourceManager` **полностью изолирован от файловой системы** и зависит исключительно от `CpuResourceManager&` (внедряется через конструктор). Для получения данных меша или текстуры он вызывает типизированный `CpuResourceManager::GetAsync<T>`, не зная ни про диск, ни про `IoScheduler`.
      - При завершении приложения `Engine::Destroy` вызывает `m_CpuResourceManager->Stop()`, который останавливает внутренний поток I/O.
      - Воркеры оборачиваются в `try ... catch` и гарантированно вызывают `Resolve` соответствующей таблицы ресурсов (100% соблюдение контракта No-Hang в состоянии Running).

## 5. Подсистема Логирования (Logging System)

### 5.1. Потоковая модель и бродкастеры
- **Игровой поток:** Записывает сообщения в лок-фри буфер `DoubleBufferedVector<LogEntry>` без задержек.
- **Поток раздатчика (`Logger`):** Событийно забирает пакеты логов и рассылает слушателям (`ConsoleBroadcaster`, `NetworkBroadcaster`).
- **Сетевой Viewer (`RemoteLogViewer`):** Принимает логи по TCP (порт 3030).

### 5.2. Уровни и режимы логирования (`DOut*`)
Поддерживаются уровни: `DOut`, `DOutWarning`, `DOutError`, `DOutException`, `DOutCritical`, `DOutFatal`.
Макросы логирования поддерживают 4 режима передачи аргументов:
1. **Обычный вывод:** `DOut("Сообщение: {}", val)`
2. **Throttling по итерациям:** `DOut(100, "Каждый 100-й вызов: {}", i)`
3. **Throttling по времени:** `DOut(0.5f, "Не чаще раз в 0.5с: {}", fps)`
4. **Условный вывод по `bool`:** `DOut(condition, "Сообщение только при true: {}", val)`

### 5.3. Отладочные переменные и флаги (`Z_LOG_VAR` / `Z_LOG_GLOBAL_VAR`)
В [src/engine/utils/EngineLogFlags.h](file:///c:/Workspaces/ZzzTest/src/engine/utils/EngineLogFlags.h) реализованы макросы отладочных переменных:
- `Z_LOG_VAR(type, name, init)` — локальная переменная логирования.
- `Z_LOG_GLOBAL_VAR(type, name, init)` — глобальная отладочная переменная с поддержкой `inline`.
- `Z_LOG_SET(name, val)` — присвоение значения.
- `Z_LOG_GET(name)` — чтение значения.

> **Нулевой оверхед в Release:** В сборках без логгера (`#if !(Z_ADD_LOGGER || Z_DEVELOPMENT_BUILD)`) макросы превращаются в `((void)0)` и `false`, а глобальные переменные не компилируются.

### 5.4. Синхронное подавление спама при ресайзе
Глобальный отладочный флаг `zzz::engine::g_IsResizing` автоматически взводится в `true` во `View` во время интерактивного перетаскивания рамок окна мышью (`OnWindowResizeStart` ... `OnWindowResizeEnd`).
Все подсистемы рендера (`View`, `SurfView_DX`, `Swapchain_DX`, `DepthBuffer_DX`) синхронно проверяют `!Z_LOG_GET(g_IsResizing)`, отсекая поток промежуточных логов кадра и выводя 1 итоговый лог по завершении ресайза.

### 5.5. Строковые хелперы GAPI (`ToStringHelpers.h`)
В [src/core/utils/ToStringHelpers.h](file:///c:/Workspaces/ZzzTest/src/core/utils/ToStringHelpers.h) (вместе с утилитами ядра `Macroses.h`, `Converters.h`) реализованы универсальные функции `ToString` и специализации `std::formatter` для прямой конвертации и печати перечислений GAPI (`DXGI_FORMAT`, `D3D_FEATURE_LEVEL`, `VkFormat`, `MTLPixelFormat`):
```cpp
#include "core/utils/ToStringHelpers.h"

// Работает как для обычного ToString(), так и для std::format / DOut
DOut("Формат глубины: {}", c_DefaultDepthFormat);
// Вывод: Формат глубины: DXGI_FORMAT::DXGI_FORMAT_D24_UNORM_S8_UINT
```

## 6. Пайплайн Сцен, Ресурсов и Пользовательских Данных (Scene & Resource Pipeline)

### 6.1. Общий поток: Assets Builder → Engine
1. **Assets Builder** (C#, `assets_builder_lib` + нативный `assets_builder_dll`) сканирует `Assets/` и `Assets/Scripts/` через единый реестр `AssetImporterRegistry` (расширение → `IAssetImporter`/`eResourceType`, см. 1.1). Генерирует/проверяет `.meta`-файлы для валидных ресурсов, валидирует `project.json` (включая обязательные `company_name`/`app_name` — см. 6.3), затем до упаковки нативная часть строит единый глобальный реестр GUID сцен, представлений, скриптов, ресурсов, слоёв и объектов. Повторы между любыми категориями запрещены; GUID-ссылки проверяются по существованию и ожидаемому типу.
1.1. **Контракт единого импорт-пайплайна (Пункт 21, 2026-09-18):**
   - Единая точка правды на расширение — `AssetImporterRegistry`: `GetImporter(ext)` для блоб-ресурсов `data.dat` (`Mesh`/`Material`/...), `GetKnownType(ext)` — более широкая проверка "известно ли расширение вообще" (покрывает и структурные `package.dat`-ресурсы вроде `Scene`/`View`, не имеющие блоб-импортёра). Оба сканирующих прохода (`ProjectIdentityValidator`, `PackagePacker`) используют только эти два метода, без собственных хардкод-веток по расширению.
   - Файл в `Assets/` с расширением, не известным `AssetImporterRegistry`, останавливает сборку с ошибкой. Явные, осознанные исключения: `.h`/`.hpp`/`.cpp` под `Assets/Scripts/` (собираются отдельно в `scripts.dll`, не упаковщиком).
   - Поле `"type"` в `.meta` обязательно **только для скриптов** (`.h`/`.hpp` под `Assets/Scripts/`), так как расширение `.h` само по себе не раскрывает тип/роль скрипта. Для всех остальных ресурсов (`.obj`, `.zmat`, `.zs`, `.zv` и т.д.) тип на 100% однозначно выводится по зарегистрированному расширению через `AssetImporterRegistry`; поле `"type"` для них опционально (если указано — валидируется на совпадение с ожидаемым типом).
   - `AssetImportPipeline::TryImport` — единственная точка чтения исходника + `.meta` + вызова импортёра для блоб-ресурсов `data.dat`; импортёры не открывают файлы и не пишут архивы (см. `IAssetImporter`).
   - Сканирование `PackagePacker` ограничено `<project>/Assets/` (ранее ошибочно проходило по всему корню проекта, включая `project.json`/`build_settings`/`platforms`, что могло дать ложные срабатывания строгой проверки).
2. **Формат представлений (Views):**
   - Все файлы представлений хранятся в едином формате с расширением `.zv` (без различий в файловой структуре между типами вью).
   - Роль представления (`PrimaryView`, `ChildView`, `IndependentView`) определяется декларативно в `project.json` (`start_view`) и платформенных конфигурациях `assets_config.json` (`child_views`, `independent_views`), после чего при упаковке проставляется в TOC пакета.
3. **Единый заголовок бинарных файлов (`DatFileHeader`, 27 байт):**
   - Все `.dat` файлы движка используют универсальный заголовок `DatFileHeader`:
     `Magic (3 байта) + Version (12 байт: major, minor, patch) + entryCount (uint32_t, 4 байта) + timestamp (uint64_t UTC ms, 8 байт)`.
   - **`assets/package.dat` (`ZZP`)** и **`assets/data/data.dat` (`ZZD`):** время сборки `timestamp` синхронно фиксируется Asset Builder'ом с точностью до миллисекунды (соответствует `yyyy-MM-dd HH:mm:ss:fff` в `buildtime-data.txt` и `assets_config.json`) и в рантайме движка никогда не меняется. Поле `entryCount` отражает количество упакованных ассетов.
   - **`user.dat` (`ZZZ`):** файл настроек пользователя в каталоге User Data. При каждом сохранении (`UserSettingsManager::SaveConfig()`) заголовок перезаписывается с текущим системным временем UTC (`timestamp`). Поле `entryCount` равно `0`. Тело файла хранит только пользовательские настройки (состояние окон View, выбранный GPU, отключённые категории логов).
4. **Нативный упаковщик** (`PackagePacker.cpp`, вызывается из C# через `PackProjectNative`) сериализует:
   - Структуру и манифест игры в единый бинарный `package.dat` (`assets/package.dat`): `project.json`, сцены (`.zs`), представления (`.zv`);
   - Игровые ресурсы в бинарный архив `data.dat` (`assets/data/data.dat`): меши (`MeshData` из `.obj` через `ObjImporter`), материалы (`.zmat` через `MaterialImporter`), шейдеры, префабы.
   - Записи обоих архивов имеют фиксированный размер (`PackageEntry::BinarySize()` = 292 байта, включая `FixedLengthString32<c_MaxAssetNameLength>`), позволяя считывать TOC блоками фиксированного размера без загрузки данных файлов в память.
   - Публикация атомарна (2026-09-18): оба архива сначала полностью пишутся в `.tmp`, рабочие `package.dat`/`data.dat` заменяются через `fs::rename` только после успеха обоих; между двумя `rename` нет кросс-файловой транзакции (см. `PackagePacker.cpp`, публикация архивов).
5. При старте движка `PackageManager::Initialize()` и `DataAssetsManager::Initialize()` считывают заголовок (`DatFileHeader::BinarySize()` = 27 байт) и блок записей TOC (`entryCount * PackageEntry::BinarySize()`), проверяют сигнатуры (`ZZP` / `ZZD`), версию и строят быстрый индекс по GUID и имени. В обычном режиме payload вычитывается точечно по требованию (`ReadBytes` по смещению и размеру конкретной записи `PackageEntry`). При включённом `Z_ADD_LOGGER` полное диагностическое логирование намеренно десериализует записи пакета для визуального контроля результата Assets Builder; такой запуск не используется как эталон измерения startup I/O.
6. `Path::InitializeUserData(companyName, appName)` строит двухуровневый каталог пользовательских данных (`%LOCALAPPDATA%/<company>/<app>/` на Windows и аналоги на других платформах) — до этого вызова `GetUserDataDirectory()`/`GetCacheDirectory()`/`GetSavesDirectory()`/`GetLogsDirectory()` бросают исключение (см. `ensure()`).
7. `SceneManager` загружает и выгружает сцены (`LoadScene`/`LoadSceneByName`/`UnloadScene`), `View` хранит `weak_ptr<Scene>` на активную сцену. Ресурсы сцены (например, `MeshData` объектов) извлекаются по GUID из `DataAssetsManager`.

### 6.2. Модель сцен
- GUID сцены хранится в её `.meta`. Каждый слой и каждый объект дерева содержит собственный неизменяемый GUID в JSON сцены; все они входят в общее глобальное пространство GUID проекта.
- `LayerData` содержит GUID, имя, тип и объекты. Порядок `layers[]` сохраняется без сортировки и является порядком слоёв для отрисовки.
- Объекты находятся только в `layers[].objects` и задаются вложенным деревом. Упаковщик рекурсивно разворачивает каждый слой в preorder-плоский список: родитель всегда расположен раньше потомка, `parentIndex` локален для массива объектов слоя. Корневой массив сцены `objects` и неявный слой не входят в актуальный формат.
- На этапе 18 `isEntity` однозначно маршрутизирует узел либо в `ObjectDomain`, либо в `EntityDomain`; `NodeBindings` хранит вид домена и его handle. В плоский `DefaultSpatialStorage` входят только узлы с мешем. `isActive` сохраняется, но пока не имеет runtime-семантики.
- `Scene` создаётся через `SceneManager`. Сейчас полное CPU-построение неопубликованной сцены выполняется в `SceneLoader`, а регистрация, `InvokeStart()` и передача во `View` — через очередь игрового потока. Этапы 17–18 эту границу потоков не меняют; пользовательская инициализация скриптов уточняется в этапе 23, владение задачами и завершение `SceneManager` — в этапе 49.
- `SceneManager::Update()` вызывается **строго один раз за кадр**, до `ViewManager::Update()`, из `Engine::OnUpdateSystem()` — логика мира (Model) обновляется строго до параллельного `Update`/`PrepareFrame` (поток 1) и `RenderFrame` (поток 2) пайплайна `ViewManager` (View).
- Загрузка/выгрузка сцен во время итерации (например, вызванная скриптом текущей сцены) и полная модель active/paused/unloading сознательно отложены в этап 49.

### 6.3. Имя компании/приложения и каталог пользовательских данных
- `project.json` содержит обязательные строковые поля `company_name` и `app_name` — единственный источник истины (C++ — единственный источник правды: значения читаются и валидируются как при упаковке, так и при старте движка).
- Оба поля валидируются как имена каталогов одной и той же логикой на стороне движка (`Path::IsValidDirectoryName`): запрет Path Traversal (`.`/`..`), спецсимволов `< > : " / \ | ? *` и управляющих кодов, зарезервированных имён Windows-устройств (`CON`, `PRN`, `AUX`, `NUL`, `COM1-9`, `LPT1-9` — без учёта регистра и суффиксов вида `CON.txt`), а также завершающих точек/пробелов. Имя не подвергается автоматической коррекции («санитайзу») — несоответствие любому из правил всегда ошибка, которую обязан отклонить ещё Assets Builder при сборке ресурсов, а не молча исправить движок при старте.
- Валидация выполняется дважды: на стороне C# (`ProjectJsonValidator`, ещё до сборки, с понятным сообщением об ошибке в логе Assets Builder) и на стороне C++ при старте движка (`PackageManager::Initialize`, защитный `THROW_RUNTIME`, если поля пустые). Обе стороны вызывают одну и ту же нативную логику через P/Invoke-экспорт `ValidateDirectoryNameNative` (`BuilderApi`), с UTF-8 маршалингом строки (`[MarshalAs(UnmanagedType.LPUTF8Str)]`), так как имена каталогов пользовательских данных могут содержать не-ASCII символы (например, кириллицу).
- Опциональное поле `app_version` (строка вида `"major.minor.patch"`, например `"1.0.0"`) — версия приложения, по умолчанию `0.0.0`, если поле отсутствует или не парсится.

### 6.5. Категория логирования
Подсистема `Scene`/`SceneManager` логируется под отдельной категорией `::zzz::core::Scene` (не переиспользует `Assets`), так как `Scene` — это одновременно имя класса и потенциальное имя категории в разных единицах трансляции (аналогичная коллизия имён уже решена для `GAPI`). Полностью квалифицированное имя в `Z_SET_LOG_CATEGORY(::zzz::core::Scene)` устраняет неоднозначность с классом `zzz::engine::Scene`.
