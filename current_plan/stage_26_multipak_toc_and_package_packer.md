## 📐 Архитектурные контракты сборщика и форматов

### 1. Трёхсекционный TOC `data.dat`
`data.dat` обновляется на трёхсекционный TOC без изменения версии формата (in-place обновление черновика):
- Заголовок `DatFileHeader` для `c_DataDatFormat`:
  * Вместо одного счётчика `entryCount` хранит три счётчика:
    - `packCount` — количество записей в Манифесте паков (Таблица 1);
    - `inlineCount` — количество встроенных ресурсов (Таблица 2);
    - `externalCount` — количество внешних ресурсов (Таблица 3).
  * Единый `buildTime` (timestamp сборки) для валидации согласованности архивов.
  * Для `c_PackageDatFormat` заголовок остаётся без изменений (`entryCount`).

### 2. Заголовок DatFileHeader, автовыравнивание и структуры записей
- **Автовыравнивание в `DatFileHeader`:**
  В шапку добавляется хелпер/переменная падинга с **автовыводом размера** на основе шага выравнивания `Alignment`:
  $$\text{PaddingSize} = (\text{Alignment} - ((\text{BaseSize} + \text{sizeof(Extra)}) \pmod{\text{Alignment}})) \pmod{\text{Alignment}}$$
  * Для `data.dat` (`Alignment = 64`): $31 + 12 = 43 \to$ размер падинга **21 байт**, итоговый размер заголовка ровно **64 байта**.
  * Для `.pak` (`Alignment = 4096`, без Extra): $31 + 0 = 31 \to$ размер падинга **4065 байт**, итоговый размер заголовка ровно **4096 байт**.
- **Чистый `DataDatHeaderExtra` (12 байт, без ручных массивов padding):**
  ```cpp
  struct DataDatHeaderExtra
  {
      uint32_t packCount = 0;     // Кол-во внешних паков в Таблице 1
      uint32_t inlineCount = 0;   // Кол-во записей в Таблице 2
      uint32_t externalCount = 0; // Кол-во записей в Таблице 3
  };
  ```
- **Таблица 1 (Список типов внешних паков):**
  Хранить GUID для паков не требуется, так как имя файла (`0004.pak`, `0005.pak`) однозначно вычисляется из типа ресурса в `constexpr`.
  Таблица 1 представляет собой компактный массив типов:
  ```cpp
  // Таблица 1: список типов внешних паков (packCount элементов по 4 байта)
  eDataDatType externalPackTypes[packCount];
  ```
- **`DataPackageEntry` (Таблицы 2 и 3 — единая структура записей 52 байта):**
  ```cpp
  struct DataPackageEntry
  {
      Guid         guid;              // 16 байт
      uint64_t     offset;            // 8 байт (в data.dat для Таблицы 2, в 000x.pak для Таблицы 3)
      uint64_t     storedSize;        // 8 байт
      uint64_t     uncompressedSize;  // 8 байт
      eDataDatType assetType;         // 4 байта
      uint32_t     checksum;          // 4 байта
      uint8_t      compressionType;   // 1 байт (None = 0)
      uint8_t      padding[3];        // 3 байта
  }; // Итого ровно 52 байта!
  ```
  * Поле `packIndex` исключено из дисковых структур: привязка к файлу вычисляется в `constexpr` за 0 тактов процессора через `ArchiveTraitsBase<eDataDatType>::TypeToIndex(entry.assetType)`.

### 3. Автоматическое распределение по типам ресурсов
Сборщик не завязывается на конкретные пути папок. `AssetScanner` рекурсивно обходит `Assets/`, а тип определяется через `AssetImporterRegistry`:
- **`data.dat` (Inline, Таблица 2):** `Mesh` (0), `Material` (1), `Shader` (2).
- **Внешний пак `0004.pak` (Таблица 3):** `Texture2D` (4) (`.png`, `.dds`).
- **Внешний пак `0005.pak` (Таблица 3):** `AudioClip` (5) (`.wav`, `.ogg`).

Если ресурсов определённого типа в проекте нет (например, нет звуков), сборщик **не создаёт** пустой файл пака, и он не попадает в Таблицу 1.

### 4. Именование и заголовок файлов `.pak` на диске
- Имя файла строго состоит из 4 цифр значения enum: **`0004.pak`**, **`0005.pak`**.
- В начало каждого `.pak` файла пишется `DatFileHeader` (сигнатура `"ZPK"`, версия, единый `buildTime`), дополненный нулями ровно до **4096 байт (4 КБ)**. Полезная нагрузка ресурсов всегда начинается с выровненной страницы памяти.

### 5. Последовательный цикл сборки проектов и таргетов (Clean-Build-Copy-Delete)
Сборка каждого проекта и таргета происходит полноценно и строго **по очереди в изолированном цикле**:
1. **Очистка/удаление временной папки сборки** (например, `.build_staging/`) перед началом этапа для исключения любого мусора от прошлых билдов;
2. **Полноценная сборка архивов** во временной папке: формирование `package.dat`, `data.dat`, `0004.pak`, `0005.pak` с проверкой целостности и единым `buildTime`;
3. **Копирование готовых файлов** в целевую папку проекта/таргета (`destinationDir/assets/`) с предварительной очисткой целевой директории;
4. **Полное удаление временной папки сборки** после успешного копирования.
Такой цикл исключает гонки файлов, взаимное затирание таргетов одной платформы и не оставляет мусора на диске.

### 5.1. Трёхзвенный конвейер подготовки ассетов (Валидатор $\to$ Предсборщик $\to$ Сборщик)
1. **Валидатор (Validator):**
   - Сканирует проект, проверяет целостность файлов, валидность `.meta`, отсутствие битых GUID и синтаксис json.
2. **Предсборщик (Pre-Builder / Резолвер зависимостей):**
   - Анализирует сцены, включённые в таргет (`add_scenes`/`remove_scenes`), префабы и списки ресурсов;
   - Рекурсивно раскручивает граф зависимостей: **Сцена $\to$ GameObjects $\to$ Материалы $\to$ Шейдеры и Текстуры**;
   - На основе привязанного к материалу шейдера определяет точный состав вершинных каналов, нужный конкретной сетке (отсекая неиспользуемые атрибуты);
   - Отсекает неиспользуемые ассеты (Dead-code asset stripping);
   - Формирует финальный очищенный список необходимых ассетов и параметры их запекания.
3. **Сборщик (Builder / Packer):**
   - Выполняет упаковку строго по списку от Предсборщика;
   - Собирает внешние `.pak` файлы (текстуры, звуки), затем `data.dat` и `package.dat`.

### 6. Архитектура бинарных блобов ресурсов и модульная структура папок
Структуры блобов для каждого типа ассета изолируются в свои подпапки в `src/core/io/package/assets/`:
```
src/core/io/package/assets/
├── common/             // Общие дескрипторы потоков
│   └── BlobCommon.h    // BlobStreamDescriptor (offset, byteSize, count, stride)
├── mesh/               // Геометрия
│   ├── MeshBlobHeader.h
│   └── MeshData.h / MeshData.cpp
├── texture/            // Текстуры (задел на будущее)
│   └── TextureBlobHeader.h
├── audio/              // Аудио (задел на будущее)
│   └── AudioBlobHeader.h
├── material/
│   └── MaterialData.h / MaterialData.cpp
└── shader/
    └── ShaderData.h / ShaderData.cpp
```

- **Единый дескриптор потока `BlobStreamDescriptor` (`common/BlobCommon.h`):**
  ```cpp
  struct BlobStreamDescriptor
  {
      uint32_t offset = 0;    // Смещение потока от начала блоба (выровнено по 16)
      uint32_t byteSize = 0;  // Размер потока в байтах (выровнено по 16)
      uint32_t count = 0;     // Кол-во элементов
      uint32_t stride = 0;    // Шаг/размер элемента в байтах
  };
  ```
- **Внутридвижковый енум разметки вершин `eVertexAttribute` (`src/core/enums/eVertexAttribute.h`):**
  Связывает семантику ([`eVertexSemantic`](file:///c:/Workspaces/Zzz/src/core/enums/eVertexSemantic.h)) и бинарный формат канала в 1 компактный байт:
  ```cpp
  enum class eVertexAttribute : uint8_t
  {
      None = 0,
      PositionFloat3 = 1,       // 12 байт, Semantic: Position
      NormalFloat3 = 2,         // 12 байт, Semantic: Normal
      TexCoordFloat2 = 3,       // 8 байт,  Semantic: TexCoord
      TangentFloat4 = 4,        // 16 байт, Semantic: Tangent
      ColorRGBA8 = 5,           // 4 байта,  Semantic: Color
      BoneIndicesUInt8x4 = 6,   // 4 байта,  Semantic: BlendIndices (номера 4 костей)
      BoneWeightsFloat4 = 7,    // 16 байт, Semantic: BlendWeight (веса 4 костей)
      BoneWeightsUNorm8x4 = 8,  // 4 байта,  Semantic: BlendWeight (сжатые веса)
      TexCoord1Float2 = 9,      // 8 байт,  второй UV-канал
  };
  ```

- **Внутридвижковый енум топологии примитивов `ePrimitiveTopology` (`src/core/enums/ePrimitiveTopology.h`):**
  ```cpp
  enum class ePrimitiveTopology : uint8_t
  {
      TriangleList = 0,   // Треугольники (по умолчанию для 3D)
      TriangleStrip = 1,  // Полоса треугольников
      LineList = 2,       // Линии (дебаг-отрисовка, сетка, лазеры)
      LineStrip = 3,      // Ломаная линия
      PointList = 4,      // Точки (системы частиц)
  };
  ```

- **Правило нулевого смещения (`offset == 0`):**
  * `vertexOffset >= 96` — вершины есть всегда;
  * `indexOffset == 0` — меш неиндексированный (Non-indexed, вызов `DrawInstanced` вместо `DrawIndexed`);
  * `skeletonGuid == Guid::Empty()` — меш статичный, скелет отсутствует.

- **Заголовок меша `MeshBlobHeader` (`src/core/io/package/assets/mesh/MeshBlobHeader.h`, ровно 96 байт):**
  Позволяет CPU читать метаданные за 0 тактов (zero-copy cast), а видеокарте — копировать всю геометрию в Staging Buffer одним вызовом `std::memcpy`:
  ```cpp
  struct MeshBlobHeader
  {
      // 1. Описатель разметки вершины для ГАПИ (16 байт)
      eVertexAttribute vertexLayout[16];

      // 2. Привязка к скелету (16 байт)
      Guid skeletonGuid;          // Guid::Empty() для статичного меша

      // 3. Вершинный поток (16 байт)
      uint32_t vertexOffset;      // Смещение от начала блоба (кратно 16, всегда >= 96)
      uint32_t vertexSize;        // Размер данных (кратно 16, дополнено нулями)
      uint32_t vertexCount;       // Количество вершин
      uint32_t vertexStride;      // Шаг вершины (байты)

      // 4. Индексный поток и топология (16 байт)
      uint32_t indexOffset;                 // Смещение (кратно 16, 0 если неиндексированный меш)
      uint32_t indexSize;                   // Размер данных (кратно 16, 0 если нет индексов)
      uint32_t indexCount;                  // Количество индексов (0 если нет индексов)
      eIndexFormat indexFormat;             // 1 байт (UInt16 = 0, UInt32 = 1)
      ePrimitiveTopology primitiveTopology; // 1 байт (TriangleList = 0, LineList = 2...)
      uint8_t  paddingIdx[2];               // 2 байта добивки до 16 байт

      // 5. AABB для Frustum Culling на CPU (24 байта)
      float aabbMin[3];           // 12 байт (X, Y, Z)
      float aabbMax[3];           // 12 байт (X, Y, Z)

      // 6. Резерв / выравнивание заголовка (8 байт)
      uint8_t reserved[8];        // Добивка ровно до 96 байт (кратно 16 и 32)
  };
  static_assert(sizeof(MeshBlobHeader) == 96, "MeshBlobHeader must be exactly 96 bytes");
  ```

- **Выравнивание 16 байт:**
  Все смещения потоков (`offset`) и размеры данных (`size`) внутри блоба строго кратны **16 байтам**, добиваются нулями при записи. Вершины начинаются сразу со смещения 96 (которое выровнено по 16 байтам).

- **Принцип атомарности ресурсов в `.dat` архивах:**
  Все ресурсы в `.dat` строго атомарны: **1 GUID = 1 конкретная сетка**. Внутри блоба не склеиваются несколько LOD'ов или вариаций. LOD'ы формируются не хранением внутри одного блоба, а атомарными ресурсами; переключение и стриминг LOD'ов управляются на уровне сцены/сущности (`Entity`), а не хранилища.
