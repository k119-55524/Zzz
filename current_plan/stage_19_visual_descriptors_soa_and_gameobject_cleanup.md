# Этап 19: Очистка NodeStorage для иерархии и матриц, очистка GameObject

## 1. Контекст, статус и цель

- **Номер этапа:** 19 (Уровень 2: GAPI-ресурсы, содержимое куба и сквозной рендер).
- **Статус:** ✅ Выполнено
- **Цель:** 
  1. Избавиться от громоздкой полиморфной структуры `VisualPayload` (`std::variant`, динамические векторы сабмешей `std::vector<Guid>`) в `GameObject` и доменах.
  2. Изолировать `NodeStorage` строго как математический контейнер пространственной иерархии и SoA-массивов локальных и мировых матриц.
  3. Очистить `GameObject` от неструктурированных визуальных данных, оставив его компактным объектом идентификации и логики.
  4. Объединить флаги состояния (`Active` и `Visible`) в плоский байтовый массив `m_Flags` в `NodeStorage` с поддержкой constexpr битовых операторов (`|`, `&`, `~`).
  5. Передать ответственность за отбор и наполнение командных буферов рендера пространственному хранилищу (`SpatialStorage`).
  6. Устранить зависимость порядка инициализации доменов от `NodeStorage`: передавать `NodeStorage&` непосредственно в метод `CreateObject` домена.
  7. Полностью удалить устаревшие файлы `src/engine/scene/visual/VisualTypes.h` и `src/core/enums/eVisualType.h` вместе с записями в `CMakeLists.txt`.
- **Зависимости:** этап 18 гарантирует стабильные `NodeHandle`, плоский `NodeStorage` и `DefaultSpatialStorage`, содержащий только узлы с мешем.
- **Следующий потребитель:** этап 20 (асинхронная загрузка мешей и жизненный цикл GameObject); этап 24 (сквозной рендер), где рендер-поток получает список видимых `NodeHandle` от spatial-хранилища.

## 2. Архитектурные решения и согласованные контракты

### 2.1. Единое хранение флагов: `Active` и `Visible` в `m_Flags` (`NodeFlags`)

Флаги состояния узла хранятся в плоском массиве `m_Flags` (`std::vector<zU8>`) внутри `NodeStorage`:
```cpp
namespace NodeFlags
{
    inline constexpr zU8 None    = 0;
    inline constexpr zU8 Active  = 1 << 0; // Активность (симуляция, скрипты OnUpdate, физика)
    inline constexpr zU8 Visible = 1 << 1; // Флаг "рендерить ли"
}
```

1. **Разделение семантики**:
   - `Active` управляет логическим обновлением объекта в кадре.
   - `Visible` управляет участием узла в конвейере рендеринга.
2. **Zero-overhead**:
   - `m_Flags` занимает ровно 1 байт (`zU8`) на узел.
   - Флаги множества узлов непрерывно упакованы в памяти.
   - Изменение активности и видимости выполняется быстрыми битовыми операциями без инвалидации стабильного `NodeHandle`.
3. **Проксирование через `GameObject`**:
   - `GameObject::IsActive()` / `SetActive(bool)` делегируют вызов в `m_NodeStorage->IsActive(m_NodeHandle)` / `SetActive(m_NodeHandle, bool)`.
   - `GameObject::IsVisible()` / `SetVisible(bool)` делегируют вызов в `m_NodeStorage->IsVisible(m_NodeHandle)` / `SetVisible(m_NodeHandle, bool)`.

### 2.2. Изоляция `NodeStorage` и роль `SpatialStorage`

1. `NodeStorage` полностью освобождён от графических дескрипторов:
   - В нём хранятся только SoA-массивы: `parentIndex`, `subtreeEnd`, локальный `Transform`, `worldMatrix`, `m_Flags` и связи `NodeBindings`.
   - Метод `ResolveTransforms()` выполняет строгий пересчёт матриц затронутых поддеревьев без ветвлений по типам геометрии.
2. Пространственное хранилище (`SpatialStorage`):
   - Регистрирует только узлы, содержащие геометрию (`objData.HasMesh()`).
   - На этапе подготовки кадра осуществляет отбор видимых узлов по фрустуму и наполняет кадровые буферы команд отрисовки.

### 2.3. Полная очистка `GameObject` от визуалов

1. Из `GameObject` полностью удалены старые визуальные поля и заглушки.
2. `GameObject` остаётся легковесным фасадом для идентификации (`Guid`, `Name`), иерархических трансформаций (делегируемых в `NodeStorage`) и пользовательских скриптов (`m_Scripts`).

## 3. Критерии приёмки (DoD)

1. Проект чисто компилируется без предупреждений через `run_build.bat`.
2. Файлы `VisualTypes.h` и `eVisualType.h` удалены из проекта и CMake.
3. `NodeStorage` инкапсулирует только пространственные трансформации, иерархию и флаги `Active/Visible`.
4. `GameObject` не содержит устаревших полей визуалов.
