# Этап 20: Асинхронная загрузка Mesh и реактивная готовность сцены

## 1. Контекст, цель и границы

- **Статус:** ✅ Выполнено (Принято пользователем)
- Этап 16 уже реализовал `ResourceManager`, `MeshLoader`, типизированный кэш, дедупликацию in-flight запросов, `DoubleBufferedVector` и доставку результатов через `CallbackQueue`. Этап 20 **расширяет существующую реализацию**, а не создаёт второй конвейер.
- **Цель:**
  1. Подключить `GameObject` к неблокирующей загрузке `Simple` и `MultiMesh` через `ResourceManager`.
  2. Для `MultiMesh` асинхронно загрузить сабмеши, сформировать в `ResourceManager` единый CPU-ресурс `Mesh` и вернуть вызывающему коду GUID итогового ресурса.
  3. Построить реактивную цепочку готовности `GameObject -> GameLayer -> Scene -> SceneManager` на существующем `CountdownTrigger`.
  4. Не регистрировать сцену в `SceneManager::m_Scenes`, не вызывать `InvokeStart()` и не передавать её во `View` до завершения всех обязательных загрузок текущего этапа.
  5. Сохранять исходный текст ошибки и доставлять её в управляющий поток, где она попадает в корневой `catch` метода `Engine::Run()`.
- **Границы:**
  - На этом этапе готовность `Mesh` означает готовность CPU-данных. Этапы 23–24 расширят тот же барьер GPU-готовностью, материалами, текстурами и шейдерами; отдельный параллельный механизм готовности не создаётся.
  - Внутренний lifecycle компонентных скриптов не меняется. Изменяется только момент общего `Scene::InvokeStart()` — он находится после барьера готовности сцены.
  - `EntityDomain`, GPU-буферы и наполнение кадровых команд не перерабатываются.
  - Новая структура визуальных данных в `GameObject` не вводится. Материалы обрабатываются на этапе 24.

## 2. Согласованная логика

### 2.1. Загрузка пар рендера и мешей

- В `GameObject` пары хранятся строго в плоском массиве `std::vector<RenderPair> m_RenderPairs` (`meshGuid`, `materialGuid`).
- На каждую валидную пару формируются асинхронные запросы в `ResourceManager` (`LoadMeshAsync` и `LoadMaterialAsync`).
- Возвращённые из коллбэков результаты сохраняются напрямую в соответствующую пару массива `m_RenderPairs[i]`.
- Для составных `MultiMesh` `ResourceManager` умеет объединять сабмеши через `CombineSubmeshes` и возвращать итоговый runtime GUID.
- Ошибка любого обязательного ресурса завершает инициализацию ошибкой через `std::unexpected`.

### 2.2. Готовность объекта

- `GameObject::Initialize(..., onReady)` всегда завершает свой контракт ровно одним вызовом `onReady`:
  - объект без мешей (`!data.HasMesh()`) сообщает готовность немедленно;
  - объект с мешами отслеживает параллельную загрузку всех ресурсов пар через `CountdownTrigger` и сообщает готовность по его завершению;
  - ошибка передаётся через `std::unexpected`.
- Динамические новые объекты инжектируются в сцену строго по факту их полной готовности, поэтому `NodeFlags::Visible` не используется как временный маркер загрузки.
- Начальная видимость узлов `NodeStorage` остаётся стандартной (`NodeFlags::Visible`).

### 2.3. Готовность слоя и сцены

- `GameLayer::Populate(..., onReady)` создаёт триггер по числу создаваемых `GameObject`. Каждый объект уменьшает счётчик после собственного завершения; пустой слой завершается немедленно.
- Ошибки объектов сводятся к первой ошибке слоя. Финальный callback слоя вызывается один раз после завершения счётчика.
- `Scene::Initialize` использует существующий счётчик слоёв, но слой уменьшает его только после своего полного `Populate` и готовности входящих в него объектов.
- `SceneManager` удерживает создаваемую `Scene` до финального результата. Только успешный callback сцены, доставленный на главный поток, выполняет последовательно:
  1. регистрацию сцены в `m_Scenes`;
  2. `scene->InvokeStart()`;
  3. пользовательский `onComplete(scene)` для последующего подключения к `View`.
- При ошибке сцена не регистрируется и не запускается; исходный текст ошибки доставляется на главный поток и пробрасывается в `Engine::Run()`.

### 2.4. Валидность callback и время жизни

- Проверка `if (callback)` подтверждает только наличие вызываемого объекта и не способна проверить захваченный сырой указатель. Поэтому валидность запроса является ответственностью `ResourceManager` совместно с контекстом загрузки сцены.
- **Ревизия:** механизм слабого токена владельца (`OwnerToken`/`IsOwnerAlive`), которым эта секция ранее описывала защиту доставки, признан избыточным и выносится из этапа 20. Взамен вводится подписка на одноразовое готовностное событие ресурса — полная проработка (`OneShotEvent`, `ResourceRecord`, потокобезопасность, CPU/GPU-таблицы) вынесена в отдельный [этап 22](stage_22_resource_manager_ownership_and_ready_events.md). Здесь фиксируется только требуемый контракт, без привязки к конкретному механизму.
- Контекст загрузки удерживает `Scene` до успеха или ошибки. При отмене/завершении движка контекст инвалидируется; недоставленные результаты такого контекста пропускаются.
- Исполнение результата и уничтожение загружаемой сцены сериализованы на главном потоке. Результат с `GameObject*` не исполняется после инвалидации контекста.
- Фоновый поток не бросает исключение наружу. Низкоуровневая ошибка сохраняется в `std::expected`; неожиданные исключения перехватываются и доставляются тем же путём как ошибка первоисточника.

## 3. Изменяемые компоненты

1. `src/engine/resources/ResourceManager.h/.cpp` — асинхронные запросы ресурсов и безопасная доставка результата/ошибки. Владение и подписка на готовность (замена owner token) — предмет отдельного [этапа 22](stage_22_resource_manager_ownership_and_ready_events.md), не этого этапа.
2. `src/engine/scene/gameobject/GameObject.h/.cpp` — массив `RenderPair`, проверка `HasMesh`, асинхронный `Initialize` и сохранение готовых GUID.
3. `src/engine/scene/layer/ILayer.h`, `GameLayer.h/.cpp` — callback готовности слоя и счётчик объектов.
4. `src/engine/scene/Scene.h/.cpp` — завершение счётчика слоями только после готовности их объектов.
5. `src/engine/scene/SceneManager.h/.cpp` — контекст загрузки, удержание сцены и единственная точка регистрации/`InvokeStart` после готовности.
6. `src/engine/scene/storage/NodeStorage.cpp` — поддержание флагов `Active` и `Visible`.

## 4. Критерии приёмки

1. Проект компилируется через `run_build.bat` без новых ошибок и предупреждений.
2. `GameObject::Initialize` не выполняет синхронного чтения мешей.
3. Объект без геометрии завершает callback сразу; объект с ресурсами завершает callback ровно один раз по готовности всех ресурсов пар.
4. Сцена отсутствует в `m_Scenes`, `InvokeStart()` не вызван и `View` не получает сцену, пока не готовы все её объекты и слои.
5. Ошибка обязательного ресурса не запускает сцену и с исходным текстом достигает `Engine::Run()`.
6. Callback отменённого или уничтоженного контекста загрузки не вызывается.
7. Поведение `EntityDomain` не изменено текущим этапом.
