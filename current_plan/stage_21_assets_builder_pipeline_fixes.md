# Этап 21: Правки сборщика ассетов (единый импорт-пайплайн)

**Статус:** ✅ Выполнено (принято пользователем 2026-09-18)

## 1. Контекст, цель и границы

- **Откуда взялся этот этап:** во время ревью незакоммиченной реализации материалов/render-пар (расширение Пункта 20) вскрылись архитектурные пробелы в самом Сборщике Ассетов (`assets_builder_dll`), не специфичные для материалов — они касаются любого зарегистрированного типа ассета. Пользователь решил вынести их в отдельный этап, а не чинить попутно внутри Пункта 20.
- **Цель:** довести build-time контракт Сборщика Ассетов до единообразного для всех типов ассетов: одна точка регистрации типа, одна политика ошибок, одна гарантия публикации архивов.
- **Границы:**
  - Рендер-пайплайн (GPU, Shader/Material runtime) не входит — это Пункты 22–23.
  - Runtime-владение ресурсами (`GC`/lease на `Mesh`/`Material` со стороны сцены) сознательно не входит — по решению пользователя: `GC` пока заглушка, отдельный технический долг на момент появления реального `GC` и рендера (см. §3).
  - Тесты по сборщику намеренно не пишутся на этом этапе (решение пользователя: «тесты побоку пока»).

## 2. Согласованная логика

1. **Единый импорт-пайплайн для всех типов ассетов — сделано 2026-09-18 (сужено).**
   `AssetImporterRegistry` расширен методом `GetKnownType(ext)` — единая точка правды "известно ли расширение", отдельная от `GetImporter(ext)` (даёт `IAssetImporter` только для блоб-ресурсов `data.dat`). `.zs`/`.zv` зарегистрированы как известные типы (`Scene`/`View`) через `RegisterKnownType`, хардкод-ветки `ext == c_ExtScene`/`ext == c_ExtView` в `ProjectIdentityValidator.cpp` убраны — оба сканирующих прохода используют только `AssetImporterRegistry`.
   **Осознанное сужение:** `.zs`/`.zv` НЕ проведены через `IAssetImporter::Import()` — их сериализация в `package.dat` (структурная, через `SerializeAssetToBinary`, завязана на JSON-обработку сцен/вью/render-пар) осталась как есть в `PackagePacker.cpp`; полное объединение с блоб-пайплайном `data.dat` — отдельная, более рискованная задача (несколько сотен строк связанной логики), не переносилась без отдельного решения. `project.json` тоже не заведён в реестр — он единственный, корневой, не часть рекурсивного скана `Assets/`, и уже имеет собственную, не менее строгую проверку.
2. **Незарегистрированный файл — всегда ошибка, единообразно — сделано 2026-09-18.**
   И в `ProjectIdentityValidator.cpp`, и в `PackagePacker.cpp` файл с расширением, не известным `AssetImporterRegistry`, теперь останавливает сборку с логом/ошибкой (было — молча пропускался в обоих местах). Исключения — `.h`/`.hpp`/`.cpp` под `Assets/Scripts/` (собираются в `scripts.dll`), проверяются явно, не по умолчанию.
   Заодно исправлено: скан `PackagePacker.cpp` раньше шёл по всему корню проекта (`sourceDir`), а не по `Assets/` — из-за этого включение строгой проверки задело бы `project.json`/`build_settings`/`platforms` ложными срабатываниями; сужено до `sourceDir/"Assets"`.
3. **Поле `"type"` в `.meta`: обязательно только для скриптов — сделано 2026-09-18 (уточнено пользователем).**
   Для всех файловых ассетов с зарегистрированным расширением (`.obj`, `.zmat`, `.zs`, `.zv` и т.д.) тип определяется на 100% автоматически по расширению через `AssetImporterRegistry`. Поле `"type"` в `.meta` для них опционально (если указано, проверяется на корректность; если отсутствует — ошибки нет).
   Поле `"type"` строго обязательно **только для скриптов** (`.h`/`.hpp` под `Assets/Scripts/`), так как расширение `.h` само по себе не задаёт тип и назначение скрипта.
4. **Атомарная публикация `package.dat`/`data.dat` — сделано 2026-09-18.**
   Оба архива сначала полностью пишутся в `.tmp`, рабочие файлы заменяются через `fs::rename` только после успеха обоих (`PackagePacker.cpp`, публикация архивов). Остаточное ограничение: между двумя `rename` нет кросс-файловой транзакции — если первый `rename` пройдёт, а второй нет, пара `package.dat`/`data.dat` рассинхронизируется; это залогировано отдельным сообщением, а не скрыто.
5. **Маршрутизация `DedicatedFolder`-ресурсов — решено 2026-09-18 (отложено).**
   Решение пользователя: текстуры пока пропускаем. Маршрутизация `DedicatedFolder`-ресурсов сознательно отложена до Пункта 23 (где они непосредственно понадобятся для пайплайна материалов и рендера). Текущий этап сборщика не блокируется.
6. **Документирование контракта — сделано 2026-09-18.**
   - `docs/ARCHITECTURE.md` §6.1 обновлён (новый §6.1.1 фиксирует реестр, ошибку на неизвестном типе, политику поля `type`, атомарную публикацию).
   - `stage_09_package_resource_formats.md` актуализирован (формат `.meta`, автоматический вывод типа меша).
   - `src/tools/assets_builder/README.md` актуализирован (контракт регистрации типов, правила сканирования `Assets/`, требования к `.meta` для скриптов и файловых ассетов, атомарная публикация).
7. **Устранение дублирования скана `Assets/` между двумя проходами — сделано 2026-09-18 (частично, см. границы ниже).**
   Отдельное архитектурное ревью (после пунктов 1–6 этого этапа, по инициативе пользователя — "есть архитектурно большие файлы? есть что поделить?") выявило, что `PackagePacker::PackProject` и `ProjectIdentityValidator::Validate` делали независимый `recursive_directory_iterator` по `Assets/` каждый — дублирование, из-за которого правки политики скана (как в пункте 2 выше) приходится вносить в двух местах синхронно. Выделен общий `AssetScanner.h/.cpp` (`ScanAssetsDirectory`) — единая точка обхода (пропуск `.meta`/не-regular, разовый `GetKnownType`), используется теперь обоими проходами.
   **Побочная находка при ревью:** правка пункта 2 (незарегистрированный файл → ошибка) была асимметричной — исключение под `Assets/Scripts/` в `ProjectIdentityValidator.cpp` покрывало только `.h`/`.hpp`, без `.cpp`, хотя `.cpp`-файлы реализации скриптов реально существуют в `zzz_assets_test_000`. Без фикса `Validate` останавливал бы сборку этого же проекта ошибкой "Незарегистрированный тип ассета '.cpp'". Исправлено симметричным пропуском `.cpp` под `Assets/Scripts/` (без требования `.meta` — идентичность несёт `.h`).
   **Границы (не сделано в рамках этого пункта, остаётся отдельной работой при желании продолжить):** вынос парсинга `build_settings`/platform-config (`PlatformConfigParser`) и парсинга сцены/`GameObject` (`SceneJsonParser`) из `PackagePacker.cpp`, распил `SerializeAssetToBinary` (~550 строк) по типам ассетов, распил `ProjectIdentityValidator::Validate` (~640 строк) на приватные методы по стадиям — всё это обсуждено и приоритизировано, но не реализовано.
8. **Очистка устаревшего рудимента `zzz_assets_test_000_build` — сделано 2026-09-18.**
   Вычищены устаревшие fallback-ссылки на локальную папку `zzz_assets_test_000_build` из платформенных файлов `CMakeLists.txt` (`game_win`, `game_linux`, `game_macos`, `game_android`, `game_ios`), тестового проекта ассетов и тестов сериализации. Сборщик ассетов централизованно собирает пакеты в `%LOCALAPPDATA%\Zzz\AssetsBuilder\.build\`.

## 3. Фиксация текущего состояния (Пункт 20, приостановлен на этом этапе)

Незакоммиченная реализация материалов и render-пар (расширение готовности `GameObject -> GameLayer -> Scene -> SceneManager` на материалы) на момент остановки:

**Сделано:**
- `Default.zmat` + `Default.zmat.meta` в `Assets/Material/`.
- `MaterialData` (`core/io/package/`) и чтение в `DataAssetsManager`.
- `MaterialImporter` в `assets_builder_dll`, тип `eResourceType::Material`, упаковка в `data.dat`.
- Класс ресурса `Material` и `MaterialLoader` в движке, `LoadMaterialAsync`, фоллбэк-заглушка в `ResourceManager`.
- Формат `MainScene.zs`: `"render": [{ "mesh": "...", "material": "..." }]`; парсинг и валидация в `PackagePacker.cpp` / `ProjectIdentityValidator.cpp` (после правок этого этапа — обязательные `mesh`+`material` в каждой записи, пустой массив допустим, пустые GUID не пишутся).
- `RenderPair { meshGuid, materialGuid }` на `GameObject`; подсчёт ресурсов и синхронизация загрузки через неблокирующий `CountdownTrigger` в `GameObject::Initialize`.
- Каскад готовности: ресурсы ГО → `GameObject` → `GameLayer` → `Scene` → `SceneManager` (расширение существующего каскада Пункта 20 на материалы).
- Убраны промежуточные обёртки/`if (script != nullptr)` в `ScriptStorage`, `GameObject`, `Scene`, `View`; `ScriptStorage` теперь сразу даёт `THROW_RUNTIME` с точным GUID/именем при отсутствующем скрипте.

**Сознательно отложено (не дефекты, а решения пользователя):**
- GC — заглушка; ресурсы сценой явно не удерживаются (`shared_ptr`/lease) — вернуться, когда появится реальный `GC` и рендер.
- `ResourceManager::AddMaterial()` — пустая заглушка, как и было.
- Тесты на `MaterialData`, битый `.zmat`, загрузку материала, render-массив — не пишутся.

**Открыто на момент паузы (актуально после завершения этого этапа):**
- Ошибка исходного `.zmat` (битый JSON, недоступный файл) — должна становиться ошибкой сборки, а не молча использовать `ctx.assetName`. Пересекается с §2.2 этого этапа (единая политика ошибок импортёров), решается тем же централизованным `AssetImportPipeline`.
- Повреждённый payload материала в `data.dat` — `MaterialLoader` должен пробрасывать ошибку `DeserializeAsset<MaterialData>()` вместо создания ресурса по имени из `PackageEntry`.

**Возврат:** после завершения и приёмки Пункта 21 — продолжить с открытых пунктов выше, статус Пункта 20 остаётся `⏳ В процессе` до явного подтверждения пользователем.
