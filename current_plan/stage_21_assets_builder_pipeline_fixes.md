# Этап 21: Правки сборщика ассетов (единый импорт-пайплайн)

## 1. Контекст, цель и границы

- **Откуда взялся этот этап:** во время ревью незакоммиченной реализации материалов/render-пар (расширение Пункта 20) вскрылись архитектурные пробелы в самом Сборщике Ассетов (`assets_builder_dll`), не специфичные для материалов — они касаются любого зарегистрированного типа ассета. Пользователь решил вынести их в отдельный этап, а не чинить попутно внутри Пункта 20.
- **Цель:** довести build-time контракт Сборщика Ассетов до единообразного для всех типов ассетов: одна точка регистрации типа, одна политика ошибок, одна гарантия публикации архивов.
- **Границы:**
  - Рендер-пайплайн (GPU, Shader/Material runtime) не входит — это Пункты 22–23.
  - Runtime-владение ресурсами (`GC`/lease на `Mesh`/`Material` со стороны сцены) сознательно не входит — по решению пользователя: `GC` пока заглушка, отдельный технический долг на момент появления реального `GC` и рендера (см. §3).
  - Тесты по сборщику намеренно не пишутся на этом этапе (решение пользователя: «тесты побоку пока»).

## 2. Согласованная логика

1. **Единый импорт-пайплайн для всех типов ассетов.**
   `.zs`/`.zv`/`project.json` регистрируются как обработчики в `AssetImporterRegistry` наравне с `.obj`/`.zmat`, вместо отдельных хардкод-веток `ext == c_ExtScene` / `ext == c_ExtView` в `ProjectIdentityValidator.cpp` и `PackagePacker.cpp`. Маршрутизация после импорта идёт по `eResourceType`/`ResourceStorageTraits`, а не по расширению файла.
2. **Незарегистрированный файл — всегда ошибка, единообразно.**
   Файл с `.meta`, но без зарегистрированного обработчика останавливает сборку с логом (сейчас — молча пропускается и в валидаторе, и в упаковщике, см. ревью от 2026-09-18). Явно исключаются только известные инфраструктурные файлы и C++-исходники (`.h`/`.hpp` под `Assets/Scripts/`), они пропускаются осознанно, а не по умолчанию.
3. **Обязательное поле `"type"` в `.meta`.**
   Поле становится обязательным и должно совпадать с типом зарегистрированного импортёра (сейчас проверяется только если присутствует). Требует миграции существующих `.meta` без поля `type` (например, `cube_00.obj.meta`).
4. **Атомарная публикация `package.dat`/`data.dat` — выполнено 2026-09-18.**
   Оба архива сначала полностью пишутся в `.tmp`, рабочие файлы заменяются через `fs::rename` только после успеха обоих (`PackagePacker.cpp`, публикация архивов). Остаточное ограничение: между двумя `rename` нет кросс-файловой транзакции — если первый `rename` пройдёт, а второй нет, пара `package.dat`/`data.dat` рассинхронизируется; это залогировано отдельным сообщением, а не скрыто.
5. **Маршрутизация `DedicatedFolder`-ресурсов — решение не принято.**
   Открытый вопрос: остаются ли текстуры и другие `DedicatedFolder`-ресурсы отдельными файлами или тоже пакуются в `data.dat`. Текстурный импортёр пока не существует — не блокирует остальные пункты этого этапа, но должен быть решён до Пункта 22 (материалам нужны текстуры).
6. **Документирование контракта.**
   Итоговый контракт (регистрация → проверка asset+.meta → чтение → импортёр → накопление → атомарная публикация) фиксируется в `docs/ARCHITECTURE.md` §6.1, кратко упоминается в `general_plan.md`, актуализируются `stage_09_package_resource_formats.md` и `src/tools/assets_builder/README.md`.

## 3. Фиксация текущего состояния (Пункт 20, приостановлен на этом этапе)

Незакоммиченная реализация материалов и render-пар (расширение готовности `GameObject -> GameLayer -> Scene -> SceneManager` на материалы) на момент остановки:

**Сделано:**
- `Default.zmat` + `Default.zmat.meta` в `Assets/Material/`.
- `MaterialData` (`core/io/package/`) и чтение в `DataAssetsManager`.
- `MaterialImporter` в `assets_builder_dll`, тип `eResourceType::Material`, упаковка в `data.dat`.
- Класс ресурса `Material` и `MaterialLoader` в движке, `LoadMaterialAsync`, фоллбэк-заглушка в `ResourceManager`.
- Формат `MainScene.zs`: `"render": [{ "mesh": "...", "material": "..." }]`; парсинг и валидация в `PackagePacker.cpp` / `ProjectIdentityValidator.cpp` (после правок этого этапа — обязательные `mesh`+`material` в каждой записи, пустой массив допустим, пустые GUID не пишутся).
- `RenderPair { meshGuid, materialGuid }` на `GameObject`; подсчёт ресурсов и синхронизация загрузки через неблокирующий `CountdownTrigger` в `GameObject::Initialize`.
- Каскад готовности: ресурсы ГО → `GameObject` → `GameLayer` → `Scene` → `SceneManager` (расширение существующего каскада Пункта 20 на материалы).
- Убраны промежуточные обёртки/`if (script != nullptr)` в `ScriptStorage`, `GameObject`, `Scene`, `View`; `ScriptStorage` теперь сразу даёт `THROW_RUNTIME` с точным GUID/именем при отсутствующем скрипте.

**Сознательно отложено (не дефекты, а решения пользователя):**
- GC — заглушка; ресурсы сценой явно не удерживаются (`shared_ptr`/lease) — вернуться, когда появится реальный `GC` и рендер.
- `ResourceManager::AddMaterial()` — пустая заглушка, как и было.
- Тесты на `MaterialData`, битый `.zmat`, загрузку материала, render-массив — не пишутся.

**Открыто на момент паузы (актуально после завершения этого этапа):**
- Ошибка исходного `.zmat` (битый JSON, недоступный файл) — должна становиться ошибкой сборки, а не молча использовать `ctx.assetName`. Пересекается с §2.2 этого этапа (единая политика ошибок импортёров), решается тем же централизованным `AssetImportPipeline`.
- Повреждённый payload материала в `data.dat` — `MaterialLoader` должен пробрасывать ошибку `DeserializeAsset<MaterialData>()` вместо создания ресурса по имени из `PackageEntry`.

**Возврат:** после завершения и приёмки Пункта 21 — продолжить с открытых пунктов выше, статус Пункта 20 остаётся `⏳ В процессе` до явного подтверждения пользователем.
