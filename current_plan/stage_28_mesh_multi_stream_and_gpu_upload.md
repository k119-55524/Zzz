# Этап 28. Архитектура хранения меша, планирование стримов и подготовка к GPU Upload

**Статус:** ⏳ Не начато

> [!IMPORTANT]
> Этот файл — единственный источник истины для Этапа 28.
> В рамках этапа реализуются:
> 1. Согласованный формат хранения 3D-мешей на базе независимых потоков (Slot-Based Multi-Stream: базовый `Stream 0` + опциональные стримы `Skinning`, `Colors`, `UV1`).
> 2. Сбор требований материалов на этапе 2 сборщика (`Stage2_PackPlanner`) с побитовым накоплением галок (`requiredBuffersMask |= material.GetRequiredBuffers()`), опираясь на упакованные шейдеры из Этапа 27.
> 3. Упаковка мешей в `data.dat` на этапе 3 сборщика (`Stage3_PakBuilder`) строго по зафиксированной маске стримов (без лишних байтов в билде).
> 4. Рантайм-монтирование трёхсекционного `data.dat` и внешних паков `0.dat` в `DataAssetsManager`.
> 5. Прямой маршрут передачи стримов меша в GPU staging buffer без дублирования геометрии в оперативной памяти CPU.

## 1. Архитектурный контракт хранения меша (Slot-Based Multi-Stream)

Сетка хранится **строго в одном экземпляре** со всеми необходимыми данными. Никаких урезанных дубликатов на диске или в VRAM.

### 1.1. Базовый буфер (Слот 0 / Stream 0) — Обязательный
Присутствует у каждого меша. Имеет строго фиксированный шаг и смещения, которые **никогда не плавают**:
- `Position` (`float3`, 12 байт, offset = 0);
- `Normal` (`float3`, 12 байт, offset = 12);
- `Tangent` (`float4`, 16 байт, offset = 24, рассчитывается по стандарту **MikkTSpace**);
- `UV0` (`float2`, 8 байт, offset = 40).
- **Итоговый шаг (stride):** строго **48 байт**.

Любой шейдер (основной PBR, тени, простой unlit) гарантированно находит нужные базовые атрибуты в Слоте 0 по фиксированным смещениям.

### 1.2. Опциональные дополнительные стримы (Слот 1, Слот 2...)
Пакуются и загружаются на GPU **только тогда, когда они реально требуются материалам проекта**:
- **`Stream 1 (Skinning)`:** `BoneIndices` (`uint16_t[4]` = 8 байт) + `BoneWeights` (`unorm8_t[4]` = 4 байта или `float4` = 16 байт). Подключается только для мешей со скелетной анимацией.
- **`Stream 2 (Colors)`:** `RGBA8` (4 байта на вершину) — если художник красил вершины в Blender (для масок листвы, ветра и т.д.).
- **`Stream 3 (UV1)`:** `float2` (8 байт) — вторая развёртка под запекание света (Lightmap) или декали.

### 1.3. Битовая маска стримов
```cpp
enum class eMeshStreamFlags : uint32_t
{
    None        = 0,
    Stream0_Base = 1 << 0, // Pos(12) + Norm(12) + Tan(16) + UV0(8) = 48b
    Stream1_Skin = 1 << 1, // BoneIndices + BoneWeights
    Stream2_Color= 1 << 2, // RGBA8
    Stream3_UV1  = 1 << 3  // float2
};
```

### 1.4. Бинарный блоб меша в `data.dat`
1. **Заголовок `MeshBlobHeader`:**
   - `AABB min` (`Vec3f`), `AABB max` (`Vec3f`) — габариты для отсечения камерой (Frustum Culling);
   - `vertexCount` (`uint32_t`);
   - `indexCount` (`uint32_t`);
   - `indexFormat` (`uint32_t`: `UInt16` или `UInt32`);
   - `activeStreamsMask` (`uint32_t`: битовая маска `eMeshStreamFlags`);
   - `submeshCount` (`uint32_t`: количество слотов под материалы);
   - Массив смещений и размеров для каждого активного стрима.
2. **Дескрипторы сабмешей (`SubmeshDescriptor`):**
   - Диапазоны индексов (`indexOffset`, `indexCount`) для каждого слота материала.
3. **Блок индексов (`IndexBuffer`):** непрерывный массив индексов треугольников.
4. **Блок `Stream 0`:** массив структур базовой вершины (по 48 байт).
5. **Блоки опциональных стримов:** последовательно друг за другом (только те, чьи флаги подняты в `activeStreamsMask`).

## 2. Логика сборщика ассетов (AssetsBuilder)

### 2.1. Этап 2 сборщика (`Stage2_PackPlanner`) — накопление требований
В `Stage2_PackPlanner` при обходе сцены и объектов встречаем пары `(meshGuid, materialGuid)`:
1. Регистрируем меш в плане упаковки: `planner.RegisterMesh(meshGuid, materialGuid);`
2. Анализируем материал / шейдер: определяем, какие входные буферы ему требуются (`material.GetRequiredBuffers()`).
3. Побитово взводим галки (`|=`) в описании этого меша:
   ```cpp
   meshPlan.requiredBuffersMask |= material.GetRequiredBuffers();
   ```
4. Если дальше меш встречается с другим материалом — новые требования просто дописываются через `|=`.
5. **Результат этапа 2:** картина по каждому мешу **полностью ясна и окончательно зафиксирована**. В план упаковки занесён точный список необходимых стримов. Лишние каналы из исходника (не запрошенные ни одним материалом) отсекаются.

### 2.2. Этап 3 сборщика (`Stage3_PakBuilder`) — физическая упаковка
1. Читает исходную геометрию меша.
2. Рассчитывает тангенты через **MikkTSpace** и габариты **AABB**.
3. Пакует в `data.dat` строго те стримы, которые отмечены в `requiredBuffersMask` меша.

## 3. Рантайм-маршрут и отсутствие дублирования в RAM

- **Никаких копий в CPU RAM:** сетка не дублируется в оперативной памяти движка (`CpuMesh` как долгоживущий владелец копии вершин не используется).
- **Прямой маршрут:** данные стримов меша из смонтированного `data.dat` читаются напрямую в staging-буфер GPU для последующей загрузки в VRAM.
- **Монтирование `DataAssetsManager`:**
  - Читает трёхсекционный TOC `data.dat` (Таблица 1: типы внешних паков, Таблица 2: inline-записи, Таблица 3: внешние записи).
  - Автоматически открывает внешние паки `N.dat` (`0.dat` для текстур).
  - Предоставляет нулевое копирование через `ReadOnlyFile`.

## 5. Критерии приёмки этапа 28
1. Формат меша основан на слотах: базовый `Stream 0` (48 байт) + опциональные стримы.
2. Сборщик на этапе `PackPlanner` автоматически определяет состав стримов меша на основе использующих его материалов (`requiredBuffersMask |= ...`).
3. Меш пакуется в `data.dat` без лишних неиспользуемых данных.
4. `DataAssetsManager` успешно монтирует трёхсекционный `data.dat` и внешние паки `0.dat`.
5. Все тесты и сборка проекта проходят чисто.
