# Этап 17: GUID, JSON-иерархия и упаковка сцен

## 1. Контекст, статус и цель

- **Номер этапа:** 17 (Уровень 2: GAPI-ресурсы, содержимое куба и сквозной рендер).
- **Статус:** ⏳ Детальный план подготовлен по прямой команде пользователя; реализация начинается только после завершения и приёмки активного этапа 16.
- **Цель:** исправить идентичность и формат сцены до дальнейшей работы над runtime-хранилищами: ввести единое глобальное пространство неизменяемых GUID проекта, добавить GUID слоя в JSON/`LayerData`, перестать упаковывать объекты с пустым GUID, сделать нативную предсборочную проверку уникальности и ссылок и канонически преобразовывать JSON-дерево каждого слоя в preorder-массив с локальными `parentIndex`.
- **Зависимости:** этапы 15 и 16.
- **Следующий потребитель:** этап 18 — линейный `NodeStorage`, доменные bindings и плоский spatial.

Этот этап меняет формат `package.dat`, поэтому включает явное версионирование и обновление постоянного тестового проекта. Он не меняет потоковую модель `SceneManager`, GPU upload и жизненный цикл скриптов.

## 2. Согласованные контракты

### 2.1. Единое глобальное пространство GUID

1. Один и тот же GUID не может принадлежать двум сущностям проекта независимо от их категории. В общий реестр входят:
   - `ProjectManifest` и представления (`View`);
   - сцены;
   - скрипты всех существующих типов;
   - файловые ресурсы (`Mesh` и остальные поддерживаемые сборщиком типы);
   - слои сцен;
   - все объекты всех деревьев сцен.
2. GUID является постоянной идентичностью. Переименование или перемещение файла, сцены, слоя либо объекта не меняет GUID.
3. Источник GUID:
   - сцены, представления, скрипты, `project.json` и файловые ресурсы — соответствующий `.meta`;
   - слои и объекты — обязательное поле `guid` внутри JSON сцены.
4. Упаковщик не генерирует GUID, не исправляет его и не подставляет fallback. Генерация выполняется редактором/инструментом создания сущности и сохраняется в источнике до запуска сборки.
5. Реестр индексируется распарсенным `Guid`, а не исходной строкой. Различия регистра или текстового представления одного значения не обходят проверку повторов.
6. Единое пространство идентичности не означает единый runtime-контейнер: пакетные индексы, сцены, домены и таблицы ресурсов остаются раздельными и типизированными.

### 2.2. Канонический JSON сцены

1. GUID сцены не дублируется в `.zs`: он берётся из `.zs.meta` и записывается в `PackageEntry`.
2. Объекты разрешены только внутри `layers[].objects`. Корневой `objects` и синтетический `Default3DLayer` удаляются из актуального формата.
3. Каждый элемент `layers[]` обязан содержать непустой валидный `guid`. Порядок элементов массива сохраняется без сортировки и является порядком слоёв для последующей отрисовки.
4. Каждый объект, включая любой уровень `children`, обязан содержать непустой валидный `guid`.
5. `children` задаёт обычное дерево внутри одного слоя. Родитель между разными слоями невозможен.
6. Имена являются отображаемыми данными и не участвуют в идентичности или связывании.

Минимальная форма:

```json
{
  "layers": [
    {
      "guid": "<layer-guid>",
      "name": "World",
      "type": "Layer3D",
      "objects": [
        {
          "guid": "<object-guid>",
          "name": "Root",
          "children": [
            {
              "guid": "<child-guid>",
              "name": "Child"
            }
          ]
        }
      ]
    }
  ]
}
```

GUID-ссылки в сцене (`scripts`, `render.mesh`, `render.material`, `submeshes`, `materials`, `parts`) продолжают ссылаться на GUID соответствующих ресурсов из их `.meta`.

### 2.3. `LayerData` и бинарный формат

1. В `LayerData` добавляется закрытое поле `Guid m_Guid` без публичного setter. Поле изменяемо десериализатором, но после создания runtime-слоя считается постоянной идентичностью.
2. Конструктор:

```cpp
LayerData(
    Guid guid,
    std::string name,
    eLayerType type,
    std::vector<GameObjectData> objects = {});
```

3. Добавляется:

```cpp
[[nodiscard]] const Guid& GetGuid() const noexcept;
```

4. Порядок сериализации `LayerData`:

```text
Guid guid
string name
uint8 layerType
uint32 objectCount
GameObjectData[objectCount]
```

5. `GameObjectData::m_Guid` уже существует и сериализуется. Этап исправляет только его источник: `ParseGameObjectJson` обязан получить GUID из JSON и не может создать объект с дефолтным GUID.
6. Добавление GUID в `LayerData` несовместимо с текущим бинарным представлением. `c_GamePackageFileMajorVersion` повышается с `1` до `2`; версия `data.dat` не меняется.
7. Старый `package.dat` версии 1 отвергается по major version и должен быть пересобран из исходных ассетов. Fallback GUID и попытка угадать старую разметку `LayerData` запрещены.

### 2.4. Нативный реестр и граница C#/C++

1. Правила идентичности и GUID-ссылок принадлежат нативному `assets_builder_dll` в соответствии с правилом 6. C# не поддерживает вторую копию этих правил.
2. Внутренний нативный реестр хранит минимум:

```cpp
struct GuidOwner
{
    Guid guid;
    GuidOwnerKind kind;
    std::filesystem::path sourcePath;
    std::string jsonPath;
};
```

Конкретное имя внутреннего типа не является публичным контрактом.
3. Одна нативная реализация вызывается:
   - из C#-предпроверки проекта через узкий P/Invoke-экспорт;
   - безусловно в начале `PackagePacker::PackProject`, до импорта и до записи/замены выходных архивов, чтобы прямой вызов DLL не обходил защиту.
4. Существующие C#-валидаторы сохраняют проверки UI/JSON, не относящиеся к идентичности (например, типы полей и диапазоны значений), но GUID-уникальность и типизированные ссылки делегируют нативной реализации.
5. Ошибка содержит GUID, тип владельца и оба пути конфликта. Для вложенного объекта указывается полный JSON-путь вида `layers[1].objects[2].children[0]`.

### 2.5. Два прохода валидации

#### Проход 1 — владельцы GUID

До упаковки сканируются все поддерживаемые исходные ассеты проекта, а не только выбранные текущим платформенным пресетом:

- `.meta` проекта, сцен, представлений, скриптов и ресурсов;
- `layers[].guid` всех сцен;
- `guid` всех объектов с рекурсивным обходом `children`.

Обязательный GUID владельца отклоняется, если:

- поле отсутствует;
- строка не разбирается `Guid::Parse`;
- значение пустое/нулевое по контракту `Guid`;
- значение уже зарегистрировано другим владельцем.

Требовать именно UUID v4 при чтении не нужно: `GenerateGuidNative` создаёт v4, но существующий формат и `Guid::Parse` допускают валидные 128-битные значения другого происхождения.

#### Проход 2 — ссылки

После полного построения реестра проверяются:

- `project.json`: стартовое представление, сцены и глобальные скрипты;
- платформенные списки представлений/сцен;
- `.zv`: сцена и скрипты представления;
- `.zs`: скрипты сцены и объектов, `render.mesh`, `render.material`, `submeshes`, `materials` и `parts`;
- остальные уже поддерживаемые сборщиком GUID-ссылки.

Для присутствующей непустой ссылки обязательны существование владельца и совпадение ожидаемой категории. Пустое значение разрешается только для действительно опционального поля. Ссылка по имени вместо GUID является ошибкой.

Текущая `.meta` скрипта содержит общую категорию `script`, поэтому на этапе 17 проверяется принадлежность к категории Script и глобальная уникальность между всеми типами скриптов. Проверка конкретного базового типа (`GameScript`/`SceneScript`/`ViewScript`/компонентный `Script`) не добавляется без источника этого типа в метаданных и относится к этапу 21.

### 2.6. Служебные записи пакета

1. `ProjectManifest` использует GUID из `project.json.meta`; жёстко заданный `00000000-0000-0000-0000-000000000001` удаляется.
2. Представление использует GUID только из `.zv.meta`.
3. Синтетический `MainPrimaryView` с жёстко заданным GUID `...0002` не создаётся. Если `start_view` задан, он обязан ссылаться на существующий `.zv/.meta`; если не задан, допустимо сохранить нынешний выбор первого реального `.zv` как PrimaryView. Отсутствие любого реального представления является ошибкой сборки.
4. Служебная запись не может обходить общий реестр или занимать незарегистрированный GUID.

### 2.7. Preorder и `parentIndex`

Для каждого слоя отдельно:

1. Корневые элементы `objects[]` обходятся в исходном порядке.
2. Объект добавляется в результирующий вектор до обхода `children`.
3. `children` обходятся в исходном порядке и рекурсивно.
4. У корневого объекта `parentIndex = 0xFFFFFFFF` (`kInvalidNodeIndex`).
5. У потомка `parentIndex` равен индексу непосредственного родителя в результирующем векторе этого слоя.
6. Для любого потомка выполняется `parentIndex < childIndex`.
7. Порядок братьев и слоёв не разворачивается и не сортируется по имени/GUID.
8. Невалидная форма `objects`/`children` не игнорируется молча, а возвращает ошибку валидации.

Этап 17 гарантирует корректный плоский вход. Перестройка runtime-топологии, линейный расчёт мировых матриц и устранение повторного dirty-обхода выполняются в этапе 18.

### 2.8. Runtime-адаптация слоя

1. `ILayer` получает GUID в конструкторе, хранит его без публичного setter и предоставляет `GetGuid()`.
2. Конструкторы `GameLayer` и `LayerMVVM` принимают GUID и передают его в `ILayer`.
3. `Scene::Initialize` создаёт слои в порядке `SceneData::GetLayers()` и передаёт `layerData.GetGuid()` в конкретный слой.
4. `GameLayer::Populate` продолжает передавать плоский массив объектов в `NodeStorage` и маршрутизировать `isEntity`; переработка bindings/domains/spatial остаётся этапом 18.
5. `SceneData::LogFileBlock` выводит GUID каждого слоя для существующего визуального контроля результата Assets Builder.

## 3. Порядок реализации

### Шаг 1. Формат ядра и версия пакета

- Добавить GUID, конструктор, `GetGuid()` и сериализацию в `LayerData`.
- Обновить вывод слоёв в `SceneData::LogFileBlock`.
- Повысить `c_GamePackageFileMajorVersion` до 2; `c_DataPackageFileMajorVersion` оставить без изменения.
- Адаптировать все места конструирования `LayerData`.

### Шаг 2. Нативный реестр и единая проверка

- Реализовать внутренний реестр владельцев GUID и рекурсивный сбор идентичности сцен.
- Реализовать второй проход типизированных ссылок.
- Обеспечить единый путь ошибок с обоими владельцами конфликта.
- Вызывать проверку до любых изменений выходных архивов.

### Шаг 3. Подключение C#-предпроверки

- Добавить узкий нативный экспорт проверки проекта и P/Invoke-объявление.
- Подключить его к существующему preflight Assets Builder.
- Удалить/делегировать дублирующие C#-правила GUID, сохранив независимые проверки структуры и значений JSON.

### Шаг 4. Канонический парсинг сцены

- Удалить обработку корневого `objects` и создание неявного `Default3DLayer`.
- Обязательно читать `layers[].guid` и GUID каждого объекта.
- Использовать только рекурсивный `FlattenGameObjectJson` для объектов слоя.
- Не пропускать ошибочные GUID и JSON-узлы молча.
- Сохранить порядок слоёв, корней, братьев и потомков.

### Шаг 5. Удаление синтетической идентичности

- Использовать `project.json.meta` для `ProjectManifest`.
- Удалить fallback PrimaryView с жёстким GUID.
- Для заданного `start_view` проверять наличие соответствующих `.zv` и `.zv.meta`; без `start_view` выбирать только реальное представление с GUID из `.meta`, а не создавать синтетическое.

### Шаг 6. Runtime-адаптация

- Добавить GUID в `ILayer`, `GameLayer` и `LayerMVVM`.
- Передавать GUID из `Scene::Initialize`.
- Добавить GUID слоя в диагностический вывод `SceneData`.
- Не переносить сюда изменения `NodeStorage`, spatial, активности или потоков.

### Шаг 7. Обновление постоянных ассетов

- Добавить глобально уникальные GUID всем слоям и объектам в `zzz_assets_test_000/Assets/Scenes/MainScene.zs`.
- Обновить остальные входные данные/фикстуры, если они используют старую JSON-схему.
- Все существующие `.meta` включить в глобальную проверку и устранить обнаруженные реальные конфликты без регенерации корректных GUID.

### Шаг 8. Верификация и приёмка

- Собрать затронутые таргеты через `run_build.bat`; новые ошибки и предупреждения не допускаются.
- Упаковать постоянный проект `zzz_assets_test_000`.
- По существующему подробному логу визуально подтвердить GUID/порядок слоёв и preorder-порядок объектов в полученном `SceneData`.
- Запустить игровой таргет до успешной загрузки и начала инициализации стартовой сцены.
- Зафиксировать дату, конфигурацию и фактически выполненные проверки в этом документе.
- Новые unit-тесты и отдельный `ctest` не входят в этап по решению пользователя; существующие тестовые исходники адаптируются только если изменение сигнатур ломает их сборку.
- Статус в `general_plan.md` меняется на `✅ Выполнено` только после явного подтверждения пользователя «Шаг принят».

## 5. Критерии готовности

- [ ] GUID `LayerData` сериализуется первым полем и доступен runtime-слою.
- [ ] `GameObjectData` получает GUID из каждого JSON-объекта, включая потомков.
- [ ] Все GUID проекта проверяются одним нативным реестром до упаковки.
- [ ] Повтор между любыми категориями сообщает обоих владельцев и останавливает сборку.
- [ ] GUID-ссылки проверяются после полного сбора владельцев и по ожидаемой категории.
- [ ] В C# не остаётся второй копии правил GUID-уникальности и типизированных ссылок.
- [ ] Корневой `objects`, неявный слой, fallback GUID и синтетические GUID пакетных записей удалены.
- [ ] Слои и объекты сохраняют JSON-порядок; для каждого потомка `parentIndex < childIndex`.
- [ ] `package.dat` имеет major version 2 и старый major version не читается как новый формат.
- [ ] `data.dat` не получает лишнее изменение версии.
- [ ] Постоянный проект упаковывается, подробный лог показывает ожидаемые GUID/порядок, игровой таргет доходит до инициализации стартовой сцены.
- [ ] Результаты фактически выполненной сборки/прогона записаны с датой и конфигурацией.
- [ ] Пользователь явно подтвердил: «Шаг принят».

## 6. Не входит в этап

- Переработка `NodeStorage`, dirty tracker, bindings, Object/Entity domain и spatial — этап 18.
- GPU upload и GPU-меш — этап 19.
- Shader/Material и полная готовность ресурсов сцены — этап 20.
- Жизненный цикл и горячий путь скриптов — этап 21.
- Кадровые render-команды N/N-1 — этап 22.
- Состояния, выгрузка и дедупликация запросов `SceneManager` — отложено; дедупликация пока не является согласованным требованием.
- Runtime spawn/destroy/reparent, эффективная активность и семантика `isActive`.
- Префабы и их идентичность.
- Новые unit-тесты и преждевременные оптимизации runtime-хранилищ.
