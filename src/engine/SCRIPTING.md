/**
 * @file SCRIPTING.md
 * @brief Полное руководство и описание архитектуры системы скриптинга в движке Zzz.
 *
 * # Система скриптинга движка Zzz
 *
 * Данный документ является единым источником правды по устройству, интеграции и использованию системы
 * скриптинга в игровом движке Zzz и WPF-редакторе.
 *
 * ---
 *
 * ## 1. Архитектура и Иерархия классов
 *
 * Все базовые классы системы скриптинга расположены в пространстве имен `zzz` и `zzz::script`.
 * Физическая структура файлов в движке (`src/engine/private/core/`):
 * - `scene/GameObject.h` — Базовый игровой объект движка (`zzz::GameObject`).
 * - `scene/Scene.h` / `Scene.cpp` — Базовый скрипт уровня/сцены (`zzz::script::Scene`).
 * - `scene/scripts/ScriptRegistry.h` / `ScriptRegistry.cpp` — Единый реестр фабрик скриптов.
 * - `scene/scripts/base_script/Script.h` / `Script.cpp` — Компонентный скрипт (`zzz::script::Script`).
 * - `scene/scripts/base_script/Game.h` / `Game.cpp` — Глобальный скрипт игры (`zzz::script::Game`).
 *
 * ### Связи классов:
 * @mermaid
 * graph TD
 *     GameObject["zzz::GameObject"]
 *     Script["zzz::script::Script (MonoBehaviour-like)"]
 *     Game["zzz::script::Game (Global Script)"]
 *     Scene["zzz::script::Scene (Scene Script)"]
 *     Registry["zzz::script::ScriptRegistry"]
 * 
 *     GameObject -->|Содержит список| Script
 *     Script -->|Ссылается на| GameObject
 *     Registry -->|Регистрирует фабрики| Script
 *     Registry -->|Регистрирует фабрики| Game
 *     Registry -->|Регистрирует фабрики| Scene
 * @endmermaid
 *
 * ---
 *
 * ## 2. Описание базовых типов
 *
 * ### zzz::GameObject
 * Корневой объект сцены. Содержит уникальное имя и список прикрепленных к нему компонентных скриптов (`zzz::script::Script`).
 *
 * ### zzz::script::Script
 * Аналог `MonoBehaviour` в Unity. Предназначен для описания логики поведения конкретного объекта.
 * - Всегда привязан к одному владельцу (`GameObject* owner`).
 * - Содержит структуру событий жизненного цикла `Events` (`OnStart`, `OnUpdate(float dt)`, `OnDestroy`).
 * - Подписка на события осуществляется в конструкторе класса-наследника.
 * - В режиме редактора (`Z_EDITOR`) инстансы отслеживаются реестром для корректного сброса при Hot-Reload.
 *
 * ### zzz::script::Game
 * Глобальный скрипт.
 * - Предназначен для работы на протяжении всей жизни приложения.
 * - Не является синглтоном: в игре может существовать и работать одновременно несколько различных экземпляров глобальных скриптов.
 * - Подходит для реализации высокоуровневых систем (аудио-менеджер, менеджер сохранений, инициализаторы).
 *
 * ### zzz::script::Scene
 * Скрипт сцены.
 * - Время жизни ограничено временем активности конкретной сцены (карты).
 * - Не является синглтоном: на сцене может быть запущено несколько скриптов сцены одновременно.
 * - Подходит для управления логикой уровня, спавнерами и квестовыми сценариями.
 *
 * ---
 *
 * ## 3. Механизм регистрации скриптов
 *
 * Скрипты регистрируются с помощью шаблонного метода `ScriptRegistry::Register<T>("ClassName")`.
 * На основе базового класса типа `T` компилятор с помощью `if constexpr` автоматически определяет скрипт в нужную фабрику:
 *
 * ```cpp
 * template<typename T>
 * static void Register(std::string_view name)
 * {
 *     std::string nameStr(name);
 *     if constexpr (std::is_base_of_v<Game, T>) {
 *         s_GameFactories[nameStr] = []() { return std::make_shared<T>(); };
 *     }
 *     else if constexpr (std::is_base_of_v<Scene, T>) {
 *         s_SceneFactories[nameStr] = []() { return std::make_shared<T>(); };
 *     }
 *     else if constexpr (std::is_base_of_v<Script, T>) {
 *         s_ScriptFactories[nameStr] = [](GameObject* owner) { return std::make_shared<T>(owner); };
 *     }
 * }
 * ```
 *
 * ---
 *
 * ## 4. Генерация реестра RegisterAllScripts.cpp
 *
 * Для решения проблемы отсечения неиспользуемого объектного кода линкером (Linker dead code stripping) в статической сборке игры, редактор автоматически сканирует дерево пользовательских скриптов и генерирует служебный файл `Assets/RegisterAllScripts.cpp`:
 *
 * ```cpp
 * #include <ScriptRegistry.h>
 * #include "Player.hpp"
 * #include "Enemy.hpp"
 * 
 * extern "C" __declspec(dllexport) void RegisterAllScripts() {
 *     zzz::script::ScriptRegistry::Register<Player>("Player");
 *     zzz::script::ScriptRegistry::Register<Enemy>("Enemy");
 * }
 * ```
 *
 * ---
 *
 * ## 5. Механизм Hot-Reload в Редакторе
 *
 * Горячая перезагрузка позволяет компилировать и подгружать измененные скрипты без перезапуска редактора:
 * 1. **Отслеживание изменений**: WPF-редактор при фокусе окна проверяет время изменения файлов в папке `Assets/`.
 * 2. **Компиляция**: Если файлы изменены, запускается фоновый процесс CMake, компилирующий `scripts.dll`.
 * 3. **Предотвращение блокировки файлов**: Чтобы Windows не блокировала файл `scripts.dll` на запись при повторной компиляции, `EditorEngine` делает временную копию `scripts_temp.dll`.
 * 4. **Выгрузка и Загрузка**:
 *    - Предыдущая библиотека `scripts_temp.dll` выгружается из памяти (`FreeLibrary`).
 *    - Базовый `ScriptRegistry::Clear()` очищает старые фабрики.
 *    - Новая `scripts_temp.dll` загружается (`LoadLibrary`).
 *    - Из неё импортируется и вызывается функция `RegisterAllScripts`.
 *    - Живые инстансы скриптов пересоздаются/обновляются.
 *
 * ---
 *
 * ## 6. Статическая сборка игры (game_win)
 *
 * В финальной сборке игры динамическая загрузка DLL не используется для производительности и безопасности:
 * - CMake-скрипт сборки игры на этапе генерации сканирует папку `Assets/`, находит пользовательские скрипты и генерирует `RegisterAllScripts.cpp` во временной директории сборки.
 * - Все исходные файлы скриптов компилируются напрямую в исполняемый файл игры.
 * - В функции `main()` перед запуском игрового цикла вызывается функция `RegisterAllScripts()`, гарантирующая статическую регистрацию всех игровых классов.
 *
 * ---
 *
 * ## 7. Порядок Выполнения Скриптов (Script Execution Ordering)
 *
 * Для предсказуемости игровой логики порядок выполнения скриптов на каждой итерации кадра (Tick) детерминирован и настраивается на уровне конфигурационных файлов и списков компонентов:
 *
 * ### 1. Глобальные скрипты (Game-level)
 * - Порядок выполнения задается упорядоченным списком (массивом) имен классов в глобальном конфигурационном файле проекта (`project.json` / `project.zzz`).
 * - Движок при инициализации создает инстансы в этом порядке и вызывает их апдейты сверху вниз.
 *
 * ### 2. Скрипты сцены (Scene-level)
 * - Порядок выполнения определяется упорядоченным списком в файле конфигурации конкретной сцены (`scene.json` / `map.zzz`).
 * - Скрипты уровня инициализируются и обновляются последовательно в соответствии с их индексами в массиве.
 *
 * ### 3. Компоненты на объекте (GameObject-level)
 * - Прикрепленные к `GameObject` компонентные скрипты (`zzz::script::Script`) хранятся внутри объекта в виде строго упорядоченного вектора.
 * - При вызове обновлений объекта обход и выполнение функций жизненного цикла (`OnUpdate`, `OnStart`) осуществляются последовательно по индексам вектора (в порядке их добавления на объект).
 *
 * ### 4. Координация между объектами (Событийная модель)
 * - Из-за высокой волатильности (постоянный спавн, удаление и сортировка объектов на сцене) жестко задавать порядок выполнения обновлений между разными `GameObject` не имеет смысла.
 * - Для синхронизации и координации логики между различными объектами используется событийная модель:
 *   - Зависимый объект подписывается на событие изменения состояния ведущего объекта (например, `CameraFollow` подписывается на событие `OnMoved` у игрока `Player`).
 *   - События гарантированно вызываются по завершении выполнения логики источника события, обеспечивая немедленную реакцию зависимых систем в том же кадре.
 */
